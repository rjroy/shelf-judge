# Collection Snapshot Caching

## Decision

Do not cache the current Collection RSC payload in `localStorage` under `Collection.revision`. Instead, build a compact Collection-specific snapshot, cache its assembled result in the daemon, and have the browser conditionally revalidate it with an opaque validator. Persist the validated compact snapshot in IndexedDB for reuse across full browser reloads, per the user's preference. Use the existing loading presentation while validating rather than claiming persisted data is current before the check completes. **Approved UX direction:** replace the server-rendered initial table with a client-loaded table; reconcile `.lore/reference/specs/collection/collection-filter-sort.md` (REQ-CFS-27/29) before implementation. The implementation plan itself still requires review before code changes. Measure each stage against the 200-game dataset before adopting the next stage.

## Observed baseline

The production build against a disposable copy of the user's data returned 12,433,433 bytes of HTML in roughly 2.7–3.0 seconds. The three game-list API results were approximately 3.29 MB, 3.31 MB, and 4.06 MB. Each independently assembles scoring data, taking approximately 0.5–0.7 seconds in the measured run. The page fetches them sequentially and serializes all three into the server-component payload (`packages/web/app/collection/page.tsx:50-86,130-151`). The browser rendering trace did not account for most of the observed delay. These are point measurements, not a guaranteed latency budget.

## Why revision-only browser storage is insufficient

`Collection.revision` increments on accepted collection mutations, including game and axis changes, but tournament data, prediction settings, niche settings, redundancy settings, and shelf configuration persist separately. These change page content without incrementing collection revision. **Add durable revisions to the other independently stored sources**; a composite version of the actual dependencies of each snapshot component is a reasonable freshness key. Increment each source revision only on a committed change and initialize/migrate old stores safely. The `bggDataStale` field can also change with time, and code changes require a representation/algorithm version. There is no existing cheap public revision endpoint or conditional `ETag` response. A revision check requiring a full collection read/validation may itself be costly. Browser `localStorage` introduces synchronous multi-megabyte parsing/writing and quota pressure. IndexedDB is asynchronous but still persists collection and purchase data on disk; enforce data/server identity scoping, schema checks, cache eviction, and failure fallback. A cache may revalidate on navigation or focus, but without polling or notifications cannot guarantee that already-open tabs update immediately after another tab's change.

## Snapshot contract

- Preserve ordinary and predicted score alternatives: these are distinct results, not interchangeable rows. Share only score-independent game fields. Each alternative needs its own score, display score, and score-dependent purchase-utilization projection: Collection displays and sorts utilization by those values (`packages/daemon/src/services/purchase-utilization-projection.ts:29-62`; `packages/web/lib/collection-utils.ts:330-365,403-420`). Never reuse ordinary utilization for the predicted variant. The niche list is currently used by the table only for niche positions (`packages/web/components/collection-table.tsx:354-375`), so send those positions keyed by game ID rather than a third full game list. Transfer shared fields once, preferably only table-needed fields. Preserve the existing owner-note exclusion and all ownership/filter/toggle behavior.
- Assemble one coherent snapshot in the daemon, sharing common inputs and intermediate computation. Cache the complete result in memory and share a single in-flight assembly among concurrent readers. After any relevant committed change, invalidate and recompute once. A rating can change predictions and redundancy for other games; do not patch just the edited row.
- Associate the snapshot with a validator composed from collection revision and newly added durable source revisions for tournament, prediction settings, niche settings, redundancy settings, and shelf configuration, plus time-dependent expiry and representation/algorithm version. Include a collection/server identity so a new data directory with the same counters cannot inherit an old result. Per-component dependency vectors can preserve unaffected cached work (for example, shelf config changes need not invalidate game scores), but start with a whole-snapshot invalidation if simpler.
- Store each new source revision **in its source file**, atomically replacing data and revision together. On startup, hydrate the committed revision vector into daemon memory, including migration of old files; do not maintain a separate metadata file that could disagree after a crash. All relevant writes must go through the daemon. Publish a revised in-memory vector only after the file commit succeeds. Coordinate snapshot assembly and mutation commits across these stores: read a coherent input/vector under a shared source lock, or read and compare the vector before and after assembly and retry on change. A result computed before a commit must never replace the current cached result after that commit. External file edits while running are unsupported; restart reloads the on-disk vector. Where a file format cannot safely gain a revision, explicitly use an equivalent persisted content identity rather than silently omitting it.
- Serve a conditional GET: under the same synchronization boundary, compare `If-None-Match` with the current committed vector and time-expiry/representation version **before** expensive assembly; return 304 without a body only if every dependency is known available and unchanged. Otherwise return snapshot and new `ETag`. Do not request a revision and then the body as two separate round trips. Wire conditional headers through the web proxy. The browser loads a stored snapshot/validator from IndexedDB on reload, revalidates before rendering it as current, retains the last validated response in memory, revalidates after edits/navigation/focus, and discards a response overtaken by a later mutation. Validate snapshot schema and server/collection identity, handle quota/unavailable storage as a cache miss, and keep **one stored Collection snapshot total per browser origin**, replacing the previous identity's entry after a successful validation of a new response; old identities cannot accumulate indefinitely. On failed validation, do not claim cached data is current or silently reuse it.
- Preserve the current page's partial-failure semantics: collection, axes, and **tournament source data needed for scoring** are required. A tournament *stats-display endpoint* failure is optional and hides only that display; it is not the same as losing tournament data used by `gameService.listGames()` and `computeScore()` (`packages/daemon/src/services/game-service.ts:712-720`). If required scoring inputs fail, show an unavailable/retry state rather than invent substitute scores. Prediction, niche, display-only stats, settings, and capacity failures degrade only their respective features. A degraded snapshot must be `Cache-Control: no-store`, carry no reusable validator, and never return 304; retry its missing inputs on the next request so recovery is visible. The client may display successfully returned portions with a clear unavailable/retry state, rather than promoting fallback data to a fresh cached result.
- Remove the full lists from the dynamic RSC page so `router.refresh()` does not re-embed them. The initial document renders a descriptive page shell, accessible loading state using the existing `packages/web/app/collection/loading.tsx` presentation, and optional no-JavaScript explanation, then the client loads or validates its snapshot. This deliberately gives up a fully server-rendered initial table; the user approved that direction, but the maintained server-component fetching requirement must be updated in the implementation workflow.

## Incremental delivery and evidence

1. Capture repeatable initial-load and post-edit timings on a disposable copy of real data: time daemon scoring, server page work, response bytes, browser parse/render, and freshness after settings/tournament changes.
2. Replace duplicated full-list transport with a table-specific snapshot while preserving both score variants, each variant's display score and purchase utilization, and niche positions. Test parity of sorting (especially utilization sort under the Predictions toggle), filters, counts, ownership, and score sources. Compare payload bytes and post-edit time. One HTTP call without shared computation is not a win.
3. Add durable source revisions and daemon memory cache with coherent invalidation. Test unchanged reads, relevant mutations across every separate store, migration of existing data, interrupted/failed writes, simultaneous reads/writes, restart, optional-source failure and recovery, and time-derived flags. Benchmark warm and invalidated reads.
4. After plan approval and spec reconciliation, add conditional fetch, browser in-memory retention, and IndexedDB persistence for validated snapshots across reloads; remove RSC re-embedding. Test 304 body absence, persistence and revalidation across reload, cross-tab revalidation on focus, stale-response races, failed revalidation, degraded responses, initial loading state, storage failure/quota eviction, and data isolation across server/collection identity. Compare repeat navigation, reload, and post-edit latency.

The cache can avoid computation on unchanged reads. A real edit that affects scoring still requires a new snapshot; compact shared assembly targets that cost. `localStorage` is not the first optimization.

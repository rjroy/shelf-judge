# Proposed contract amendments for Jev redundancy similarity

## Status and decision boundary

The [approved similarity design](.lore/work/design/jev-redundancy-similarity.md) establishes the direction. The owner approved these contract amendments on 2026-09-29. The four reference documents below govern the running application and must carry the approved target contract; implementation and each actual outbound note refresh remain separately gated. Approval of this artifact does not itself send notes to TypeSafe or permit silent transmission. Reconcile each reference's examples, requirements, technical contract, exclusions, and validation as one change before planning implementation.

The cross-document rule is: a normal redundancy read is deterministic and offline; only an explicit, disclosed owner-triggered analysis sends evidence to the daemon-owned typed-Jev capability; the current note is never an instruction or an automatic rating. No client, route, or feature engine owns a provider connection.

## 1. Owner notes: narrow model-use exception

**Target:** `.lore/reference/specs/current/owner-game-notes.md`, especially Goal; Recording Why A Game Belongs; Privacy And Security Boundary; REQ-GAME-NOTE-6/7/12/20/21/25/26; Derived Artifacts; Out Of Scope; AI Validation. Preserve the rest of the existing note lifecycle, strict broad-response omission, and offline CRUD contract.

**Proposed addendum to the privacy/meaning contract:**

> Owner notes remain local testimony and never become ratings, verified experiences, instructions to a model, or ordinary profile input. A separate Jev redundancy feature may use the *current* `present` note of two eligible games as evidence for a similarity judgment **only** during an explicitly requested refresh whose disclosure names TypeSafe/Jev, the pinned model, the exact selected pair set, which pairs include notes, the transmission/retention implications, estimated request budget, and the possibility that cached similarity changes integrated fitness. An owner-note edit, clear, read, profile read, BGG refresh, or background job cannot initiate transmission. Missing and cleared notes must not be transmitted or reconstructed. Declining note use leaves C-only description analysis available.

> A refresh authorization covers one displayed pair set and one execution, not future refreshes or newly eligible games. Separately configured permission to *use* already cached D in annotation/integrated scoring is not permission to retransmit notes. Before each request, verify the current authorization, pair eligibility, note versions and state, and that neither note changed since disclosure. If any premise changes, stop unsent work and require a fresh disclosure/authorization. Disable/revoke transmission to stop new requests and cancel in-flight requests where possible; fence publication even if cancellation fails. Disabling cached D use withdraws its active generation and purges D and shared-request C entries before success is observable. Revocation does not claim to erase provider-held copies of already transmitted text.

> The revisioned collection is the **single authority** for Jev consent and publication: persist semantic enablement, F/C/D weights, cached-D-use permission, active refresh authorization (job ID, disclosed pair-set and source identity, provider/model, remaining permitted execution), pair cache, and published-generation pointer there under the serialized collection mutation coordinator. Persist no note text in consent/job metadata. A request authorization is consumed/closed when its one execution ends and cannot be reused after restart; a resumable refresh requires a new explicit authorization. Do not mirror these permission flags in the separate legacy `redundancy-settings.json`; that file remains authoritative only for existing factual redundancy settings/stage/threshold. Revocation or semantic-weight change is one atomic collection mutation that removes/withdraws disallowed scores and active refresh permission before returning success. Each outbound request checks the current collection authority immediately before submission, and any changed collection revision/consent epoch fences publication. Readers accept a generation only when its consent epoch, enabled weights, and source identity still match that same collection revision. A settings PATCH that affects factual similarity additionally withdraws the active generation under the serialized mutation path before it is reported successful; cross-file writes must not create a window where a revoked generation is served. If this cannot be made atomic, block the PATCH rather than fall back to a transient in-memory flag.

> Notes sent in shared C+D state are visible to the provider for *both* answers even when C's instructions say to ignore notes. Thus C from that request inherits note-version/authorization dependencies; a C-only request contains no note fields at all. Cache only numeric answers and minimal provenance in the revisioned collection; never persist prompts, note excerpts, free-form model explanations, prior note text, or real note text in logs. If a note is edited, cleared, or its game deleted, withdraw/purge dependent active results in the same accepted collection mutation; discard stale in-flight completions. Independently persisted note-derived profile/displayed-score artifacts must be invalidated before the mutation becomes observable. If required invalidation or collection persistence fails, do not report note-mutation success.

> The artifact lifecycle also fences **writers**: a profile/displayed-score computation captures the current collection source revision, semantic-generation identity, and consent epoch. Its final source check **and atomic artifact write run inside the same serialized collection mutation coordinator used by note clear/revocation**, without holding that coordinator during computation or any provider request. Therefore publication either completes before a clear (and is purged before the clear commits) or sees the changed revision/consent after the clear and aborts its write. No second writer outside this coordinator may persist note-derived artifacts. Serving an artifact also checks its identity against the current collection, including after restart; the reader check is defense in depth, not a substitute for serialized publication. For note mutation and D revocation use a targeted note-derived-artifact purge; do not invoke a broad wishlist invalidator that clears factual-only wishlist snapshots. Failure to purge an independently persisted note-derived artifact aborts the note mutation; a completed purge followed by a failed collection write may require benign recomputation but leaves the original note state intact.

> D is one Jev Score comparing the pair of current `present` notes; there is no separate relevance/firsthand Noul or hard eligibility gate. The Score must reflect only what the notes document and must not invent play experiences where none are documented. Validate confidence as metadata, but confidence does not filter or downweight a valid score. Do not substitute ratings, BGG description, play comments, or historical note text. Owner-note mutations and normal reads remain offline and inference-free even if this optional feature is configured.

**Requirement reconciliation:** narrow REQ-GAME-NOTE-21's universal no-model/no-transmission statement to the operations it enumerates, with this one owner-triggered exception. REQ-GAME-NOTE-7 and -26 still prohibit automatic conversion into source ratings, collection roles, or profile claims; explicitly allow an authorized **derived pairwise redundancy signal** and its integrated-mode effect, rather than implying the note itself changes. Keep REQ-GAME-NOTE-6's no-prior-text guarantee and add purge/version/publication checks for this numeric artifact. Preserve REQ-GAME-NOTE-12/20's broad response/log omission and -25's side-effect-free reads. Replace only the blanket `prompt construction or network transmission` exclusion with `unrequested or automatic prompt construction/transmission`; do not quietly loosen other exclusions. Add a representative C-only refresh and a C+D consent/edit/clear experience, and tests for consent mismatch, withdrawal, stale requests, restart, and failure compensation.

## 2. Model architecture: one owner, two capabilities

**Target:** `.lore/reference/architecture-pattern.md`, “Hard Constraint: One Daemon-Owned pi-agent Boundary,” “One Entry Point for Model Calls,” and testing seams.

**Proposed replacement boundary:**

> All model work is owned by one daemon inference gateway. Existing grounded analysis continues to use its pi-agent provider/session boundary and existing extension/tool authorization. A separately approved typed-Jev capability within that same daemon gateway may submit TypeSafe System One state and typed questions for the authorized redundancy refresh. Jev is **not** a pi-agent grounded-analysis session, and its typed answers are not free-form grounded completions. Web, CLI, routes, feature services, and pure redundancy scoring cannot create independent provider connections or call TypeSafe directly.

> The gateway owns explicit provider/model selection and pinning, TypeSafe credentials, per-refresh evidence manifest and consent check, strict question/answer validation, usage accounting, rate/concurrency/budget limits, retry/backoff and cancellation, failure categories, and redacted attempt/outcome logging. It exposes test-injectable boundaries. Caller policy limits transmitted evidence to the two current BGG descriptions and, only with separate authorization, two current owner notes for the disclosed pair; no broad collection, note history, system tools, or unrelated profile data are sent. Provider-side privacy/retention is disclosed rather than presumed local. No model call occurs in ordinary reads or note mutations.

**Reconciliation:** replace absolute claims that *all* AI necessarily passes through pi-agent/one grounded-analysis session with the gateway plus two named capabilities; preserve pi-agent requirements for existing grounded-analysis features. Add a typed-Jev testing seam for state minimization, permissions, answer validation, usage/errors, and cancellation. This is an explicit architecture amendment, not an assertion that the current pi-agent library supports Jev Score.

## 3. Redundancy: factual cosine plus published semantic signals

**Target:** `.lore/reference/specs/fitness/redundancy-scoring.md`, REQ-REDUN-1–8, -14/15, -17–24, -28–41, caching exclusion and validation. Keep prediction similarity, shelf distance, and niche clusters unchanged.

**Proposed replacement scoring/settings contract:**

> Redundancy retains its current factual binary/continuous feature encoding and *one* combined weighted cosine. Remove `personalAxes` from redundancy-only settings and similarity; do not delete personal/tournament ratings or shared feature-vector support needed elsewhere. For saved settings, preserve the binary:continuous ratio. If both factual weights were zero, migrate to 4:3 with a visible notice. Existing enabled annotation/integrated stages remain enabled, but use factual-only similarity until semantic mode is explicitly enabled. This migration can change neighbor membership and primary integrated scores even when no model feature is used; disclose it. Do not reinterpret old personal-axis weight as note weight.

> New settings separately control factual baseline weight F, description weight Cw, note weight Dw, enabled semantic signals, and the existing threshold/stage. Keep the factual binary/continuous settings in the existing settings file; store semantic enablement, **independently configurable F**, Cw/Dw, cached-D-use permission, and active publication in the revisioned collection as specified above. F weights the *already computed* factual cosine in the final blend; it is **not derived** from the sum of the binary and continuous settings. Those two settings determine the ratio *within* that cosine; a saved zero/zero ratio migrates to 4:3. Semantic mode defaults off and Cw/Dw default to zero for migrated installations; F defaults to 7 but is inert while semantic mode is off. New installations also require explicit semantic opt-in. The illustrative `4A, 1B, 5C, 10D` is **not** a new definition of A/B: retain the current factual 4:3 ratio unless the owner changes it. Proposed opt-in starting values for review are F=7, Cw=5, Dw=10 (sum 22 when all signals are available), not established calibration. Validate F as finite and >0, Cw/Dw as finite and >=0. A selected zero-weight signal is disabled and needs no inference. Distinguish an absent source from an uncached, pending, failed, stale, or insufficient-evidence judgment.

> For an eligible pair, combine `factualCosine`, `descriptionScore`, and `noteScore` only from enabled, available components by dividing their weighted sum by the sum of those components' weights. C needs two usable current BGG descriptions; D needs two current present notes and authorized cached-D use, with no separate relevance/firsthand gate. Score values are normalized to [0,1] under a versioned, owner-reviewed rubric; validate confidence as metadata but do not use it to filter or downweight a valid score. C and D may be asked as independent questions in one provider request when both inputs are authorized. Do not initiate inference from the pure synchronous redundancy engine.

> A collection semantic generation covers the currently owned, non-vetoed, positive-score games eligible for redundancy. Freeze and disclose the exact unordered pair set. Required coverage is determined solely by **enabled positive-weight signals**: C-only requires all C-eligible pairs; D-only requires all D-eligible pairs and never sends descriptions merely to fill C; C+D requires both sets. A genuinely absent required source is unavailable, not pending inference; a pair with two present notes receives one D Score judgment, without a relevance/firsthand gate. When Cw=Dw=0 semantic mode is off and no semantic generation or requests are required. A D-only request includes current authorized notes and the D Score question, without BGG descriptions; C-only includes descriptions without notes. Publish the whole generation atomically after required judgments succeed, with game/source/consent/model/rubric identities in the revisioned collection. Pending, failed, stale, and provider-outage work cannot silently renormalize an active result. If there is no valid generation, compute factual-only with a visible `not ready`/`stale` status. An accepted relevant source or eligibility change withdraws the semantic generation and returns to factual-only until an explicitly refreshed full generation is published; annotation and integrated modes use the same publication state. A published C-only or D-only generation assigns the disabled signal zero effective weight even if its text exists. Disabling D withdraws a C+D or D-only generation pending a complete C-only generation if C remains enabled, otherwise factual-only.

> The similarity threshold, neighbor ordering, and penalties use the published blended score when valid, otherwise the factual-only score; surface which mode and generation/status produced displayed adjustments. Preserve existing veto, predicted-reference authority, niche-cluster independence, and the annotation/integrated score distinction. The pure engine may consume precomputed valid scores but never provider clients or note text. A separate explicit refresh/status operation performs inference and publication. Only numeric semantic judgments are durably cached; ordinary pairwise factual cosine remains computed on demand.

**Reconciliation:** change REQ-REDUN-14's `similarity` comment from cosine-only to factual-or-blended with provenance; revise candidate-preview requirements -22/-23/-36/-39 to remain factual-only by default. Add operation discovery/CLI and settings UI contracts for enablement, disclosure, refresh status, coverage, revocation, and distinct explanation of a provisional factual score. The old “no caching” exclusion becomes “no cache for factual cosine; versioned numeric semantic judgments have a durable cache.” Update latency assumptions: 19,900 possible unordered pairs among 200 games is a budget upper bound, not a normal-read network workload. Preserve the distinction between score eligibility and note presence: do not transmit notes of excluded games merely because they exist.

## 4. Wishlist: keep stored preview factual-only

**Target:** `.lore/reference/specs/features/wishlist.md`, REQ-WISH-1/4/11/13/14/28/29 and the “same search preview codepath” wording.

**Proposed clarification:**

> `WishlistEntry.redundancyPreview` remains a durable **factual-only candidate snapshot** at add or explicit refresh time, even if a collection semantic generation is active. It stores neither D-derived numbers nor Jev text, notes, prompt content, or semantic cache identity. Wishlist entries are not collection games and have no owner note for D. An explicitly requested search/candidate semantic comparison may use C where both descriptions exist, with a candidate BGG-ID/description identity and owned-game source identity; it is transient, visibly marked C-only and never written to `wishlist.json`. Ordinary search prediction and wishlist add/refresh remain inference-free. Label persisted versus transient preview modes so a stored factual-only result is not presented as equivalent to a collection C+D result.

> A note edit/clear or cached-D revocation must not erase the factual-only wishlist decision snapshot. Source changes that already invalidate wishlist fields under their existing contract retain that behavior; implement note-specific artifact invalidation separately from general collection-artifact invalidation.

**Reconciliation:** keep snapshot-at-save semantics and the separate wishlist file intact. Amend wording that add/refresh stores the same preview visible in search: the stored preview is specifically factual-only. Keep candidate-only penalty calculation and lack of ripple preview. Cross-check Collection snapshot validation only if the public payload or validator gains new generation/status fields; do not disclose owner-note state in broad collection responses.

## Acceptance evidence for these amendments

- Each amended reference is internally coherent, uses the same source/authorization terms, and links the approved design. Existing first-release note history is retained but scoped honestly rather than rewritten as if Jev already ships.
- A reviewer can point to exactly one path for C-only requests without notes, one for C+D with explicit pair-scoped authorization, and a separate cached-D use permission; revocation and provider disclosure are explicit.
- Read, save, clear, BGG refresh, standard prediction, profile read, and background jobs cannot trigger Jev or transmit notes. Tests must prove note text is absent from broad responses, logs, persisted pair cache, wishlist, and superseded derived artifacts.
- Mutation, cache publication, and crash/restart tests establish that accepted clear/deletion cannot leave an old note-derived score observable or allow an in-flight cache/profile writer to recreate it. A failed pre-invalidation or collection write does not report successful note mutation; factual-only wishlist snapshots survive note edits.
- Existing factual-only behavior, migration of legacy weights (including 0/0), partial/failed refresh, C-only mode, integrated-mode score impact, and candidate/wishlist preview differences have explicit validation examples. Measure real Jev pair quality and cost before choosing production defaults or switching semantic mode on.

## Owner decisions confirmed 2026-09-29

1. The narrow outbound note exception is approved as a **feature contract**, with one-refresh pair-set consent, separately controlled cached-D use, C-only fallback, and explicit revocation limitations. Actual transmission still requires implementation and an explicit owner-triggered refresh.
2. The single daemon gateway with grounded pi-agent and typed Jev capabilities is the approved target architecture; direct provider calls from feature services remain prohibited.
3. Factual-only migration, separate semantic opt-in, and all-or-nothing generation publication are approved, including the disclosed possibility of offline fitness changes when redundancy personal axes are removed.
4. Initial opt-in weights are F=7, Cw=5, Dw=10; the binary:continuous ratio inside the factual cosine remains 4:3 unless changed by the owner. Selected-pair exploratory refresh may be supported in addition to collection-wide refresh but cannot publish collection fitness output.

# SQLite Jev pair cache

## Purpose and authority

This approved design amends the storage, refresh, and disclosure mechanics in the maintained [Redundancy Scoring](../../reference/specs/fitness/redundancy-scoring.md) and [Owner Game Notes](../../reference/specs/current/owner-game-notes.md), and supersedes conflicting steps in the historical [Jev similarity design](jev-redundancy-similarity.md) and [implementation plan](../plans/jev-redundancy-similarity.md). Preserve the prior documents for discovery and history. Design approval does not authorize provider calls or imply that implementation is complete.

The approved choice is a daemon-owned SQLite database for Jev's derived numeric per-pair judgments and refresh progress, instead of embedding the pair cache in `collection.json`. Collection JSON remains the authority for games, owner notes, and minimal semantic preferences/permission. SQLite is a disposable derived cache, not a second collection authority. Cache loss means cache miss and factual-only/not-ready scoring; it must never trigger Jev calls except through a fresh, explicit **Run** operation.

The earlier plan overengineered pair review into a requirement to browse or acknowledge a complete downloaded pair manifest. That is rejected: do not require pair-by-pair browsing or manifest download/inspection. Retain accurate disclosure of scope and counts, one-execution authorization for note transmission, and checks that inputs have not changed. The owner chose **Allow edits; verify inputs**, not blocking pair edits. Do not lock pairs or prevent edits while a run is active. Do not claim a physical pair lock; safety comes from source identity checks and discarding stale results.

## Decisions

- Use Bun 1.4 `bun:sqlite`, in a daemon-managed database alongside application data. One daemon process is the supported writer, consistent with collection storage. Do not expose SQLite paths or writes to clients.
- Keep current full eligible collection-pair scope for publication initially, but enumerate and process lazily. The owner sees compact scope/count/budget disclosure and progress, not a mandatory pair-by-pair review screen.
- Preserve combined C+D requests when both are enabled/eligible/authorized. Every result depends on every source included in the shared request state: C+D results depend on both games' names, descriptions, and notes (and note versions); C-only depends on both names and descriptions and contains no note fields; D-only depends on both names and current present notes and contains no descriptions. A combined C answer is not independent merely because its rubric ignores notes.
- Cache only validated successful numeric C/D judgments and minimal provenance. Do not persist request bodies, prompts, note or description text, excerpts, or free-form explanations in SQLite, collection JSON, logs, or progress state.
- Keep partial valid pair results across ordinary provider failures and restarts for reuse by a later explicit Run. A collection semantic result is active only when the complete required coverage is valid. Until then use factual-only scoring with truthful not-ready/stale status; never renormalize around pending or failed required work.
- Model/rubric/question/schema identity and exact source fingerprints are part of cache validity. No previous version is silently reused.

## Ownership and storage model

Collection JSON (schema v10) stores authoritative games and notes, semantic settings/weights, cached-D-use permission, and minimal monotonic policy/consent epochs or equivalent durable fences. It does not contain pair rows, per-pair progress, or a generation-sized pair manifest. Preserve strict public collection projections: cache metadata, note presence, fingerprints, and consent internals are not broad response fields.

SQLite stores normalized unordered pair records keyed by canonical stable game IDs and complete per-result judgment identity. It also stores one current run's compact identity/progress and an advisory activation identity, not a duplicated full generation or pair list. Rows can be deleted at any time without loss of authoritative source data. An SQLite active pointer alone never makes scores scorable: every scored read must validate collection-authoritative policy/consent, current eligibility/scope, current per-pair source identities, required complete coverage, and the activation identity. Missing, corrupt, unreadable, or mismatched state fails closed to factual-only.

The schema should separate pair identity, signal results, and run metadata sufficiently to invalidate one signal or dependency without losing independent valid work. Each signal result records at minimum:

- stable unordered game IDs (canonical ordering; no display-name keying);
- signal C and/or D numeric value in the validated normalized range, plus confidence/quality metadata as approved (confidence never gates or discounts a valid score);
- resolved pinned model identity, rubric/question version, request/state schema version, and score-mapping version;
- a mandatory collision-resistant fingerprint of the exact current game name for each game whenever a name is sent; never retain plaintext game names in SQLite;
- exact source fingerprints for each sent BGG description and owner note, plus owner note versions; distinguish C-only, D-only, and shared C+D request dependencies;
- model, rubric/question, prompt/state schema, score-mapping and semantic-policy identity, and completion time. Keep generation/policy identity separate from per-pair source identity.

Fingerprints are opaque validity aids, not content or proof of secure erasure. Hash exact sent inputs with a collision-resistant digest; do not normalize away meaningful source changes. Record per-row fingerprints/versions independently from the generation or policy epoch: changing one pair's source makes only that pair's affected result stale (for a changed game's source, all incident pairs are affected), not every unrelated result. A policy/model/rubric/schema/weight/consent change may invalidate a broader set according to its scope. The global eligible universe can change while unaffected rows remain reusable; a new or removed game changes required coverage/scope but does not by itself invalidate unrelated pair results. C depends on both names and descriptions. D depends on both names and current present notes. In a combined C+D request, both answers depend on both names, descriptions, note fingerprints, and note versions because all were in shared state, even if either rubric says to ignore some field. The dependency record must preserve those exact sent-state dependencies.

Only name fingerprints, never plaintext names, may be retained. Never store notes or descriptions in plaintext merely to recreate a request.

SQLite transactions are short and local: a transaction may claim/advance run progress, upsert validated results, purge invalid rows, or update activation metadata. A single short serialized critical section must cover the final read/verification of authoritative collection source and policy state plus the SQLite result upsert (and similarly any activation or revocation transition that spans both authorities). Collection mutations/revocations use that same coordinator so there is a total order: either a result is written while its checked inputs/policy are still current, or the conflicting mutation is ordered first and the result is discarded. Do not release the coordinator between final verification and SQLite commit. Synchronous outbound request initiation is also ordered with revocation under that coordinator; release it before awaiting the network response. No transaction or coordinator is held during a network wait. This is local sequencing, not an atomic cross-file transaction.

## Run protocol and stale-result fencing

Only an explicit user-triggered Run operation can do inference. Settings changes, status/read routes, note edits, cache misses, startup recovery, collection scoring, and background work do not invoke Jev. There is no automatic resend of unfinished pairs after restart. The user starts another Run explicitly.

1. **Prepare.** One explicit **Run** action, together with the concise required disclosure/authorization, starts the execution; there is no separate full-manifest browse, download, or pair-by-pair acknowledgement step. Under the collection coordinator, read a consistent eligible game snapshot, effective signal weights, source/consent epochs, and note versions. Enumerate the existing complete unordered eligible pair scope as an iterator; do not materialize a mandatory review/download manifest. Compute required per-signal coverage from enabled weights and genuinely available sources. Capture a compact run identity plus an exact eligibility/source identity. Disclosure states provider/model, total pair and note-bearing pair counts, signal scope, the fact that current note text may be sent and possible provider retention, budget limits/estimate, and potential integrated-fitness effect. Note authorization is one execution and covers the internally frozen disclosed note-bearing set; cached-D-use remains separate permission.
2. **Resolve hits lazily.** For each eligible pair in stable order, compute current source fingerprints and check SQLite. Reuse only successful rows matching every relevant model/rubric/question/schema identity, exact per-row sent-source fingerprint/version, and that row's relevant policy/consent dependency. Do not make an unrelated collection-wide source epoch a dependency of every row; validate collection-wide eligibility/policy identity separately for activation. Missing or invalid source is derived unavailable and needs no request. Cache misses are pending, not inferred unavailable. Update bounded progress counters; avoid sending or returning the full pair list.
3. **Pre-dispatch check.** Immediately before each request, briefly re-read authoritative source/eligibility/consent state through the collection coordinator and verify exact pair eligibility, name fingerprints, source fingerprints, note versions, current authorization, and relevant policy identity against that pair's captured inputs. Initiate the one-shot outbound request synchronously inside this short boundary, then release the coordinator before awaiting any network response or retry delay. An attempt already initiated cannot be recalled, but none may start after a serialized revocation or cancellation. If a pair changed, mark only that pair's affected requested signals stale and do not send its changed note under the old authorization; continue processing unaffected pairs. A source change to one game affects its incident pairs, not unrelated pairs. Any newly required pair after a scope change is not silently added to the old note authorization; it remains outstanding for a later explicitly authorized Run. A changed global policy, disabled signal, model or rubric does stop work whose identity no longer matches.
4. **Request.** Send only the signal-appropriate inputs. C-only omits notes entirely; D-only omits descriptions; combined C+D preserves the approved shared-state request and dependency. Validate the complete expected typed response. Malformed, partial, or out-of-range results are failures, not zero and not unavailable. Redacted logs may include attempt/outcome, pair IDs, signal, run identity and safe usage metadata, never source text.
5. **Post-response check and checkpoint.** Recompute the exact sent-state fingerprints and enter the short serialized critical section. Verify current pair eligibility, per-row input identity, authorization/policy epoch and cached-D-use permission there; only then commit the validated numeric row(s) to SQLite. If those pair inputs changed, discard only that pair response. Continue unaffected pairs. Keep valid partial cache for later reuse. No stale late response may recreate a purged row: collection mutation and result upsert are ordered through the shared coordinator, with a source/policy fence checked inside the critical section.
6. **Finish and activate.** Re-evaluate required coverage for the current eligible universe and current policy. Only if every currently required judgment is valid, all current pair identities match, and consent/cache-use permission remain valid may one short serialized critical section verify collection authority and commit the advisory SQLite activation identity. If inputs changed during the run, unaffected pair rows remain cached and reusable; only changed/added required pairs are outstanding, but the run does not activate a partial collection result. If collection/SQLite failure interrupts activation, readers fail closed to factual-only; recovery can establish readiness only by validating a complete current cache, never by provider calls. A failed/incomplete run retains valid partial rows but is not active.

Progress is resumable as cache state, not as execution authorization. On daemon restart, mark an interrupted run interrupted/available-to-rerun, discard active transmission authorization, and expose cached coverage. A later explicit Run recomputes the source snapshot and reuses valid rows; it makes fresh requests only for still-missing required entries under fresh authorization. A restart never resumes sending autonomously.

## Collection writes, notes, revocation, and file boundaries

Owner note edits must remain allowed during a run; no pair lock and no network-duration lock. On set/edit/clear or permanent deletion, acquire the brief shared collection coordinator and purge affected D and shared C rows, withdrawing their activation eligibility, **before** committing the collection JSON mutation. If SQLite purge/withdrawal fails, abort the JSON mutation and report failure. If purge succeeds but JSON persistence fails, the old source remains authoritative and only valid disposable cache rows were lost; factual-only is safe until a later explicit Run. On success, the changed pair inputs are stale while unrelated pair rows remain valid/reusable. Deletion purges all rows involving the game. A description change purges affected C rows **and D rows from shared C+D requests**, while retaining independent D-only rows. Factual score-source or eligibility changes withdraw semantic activation and invalidate affected judgments according to their dependencies; unrelated pair judgments remain reusable where their own source and policy identities still match. Previously-owned status/eligibility changes follow the current eligible universe contract.

There is no atomic transaction across `collection.json` and SQLite. Use the purge-before-JSON ordering above under the short coordinator for note/description revocation paths; the coordinator also orders final result verification/upserts so stale in-flight work cannot reinsert purged rows. If purge fails, abort the source mutation. If the JSON write fails after purge, the prior collection source remains authoritative and cache loss only requires explicit recomputation. For any path that cannot purge first, it must durably advance a collection-authoritative fence first and scored reads must check that fence before consulting SQLite; failure cannot permit stale service. Do not promise atomic cross-file edits, secure erasure, or provider-side deletion.

Disabling cached-D-use or revoking it advances the durable collection-authoritative consent/policy epoch and withdraws dependent activation before returning success, then purges D plus combined-request C rows under the same brief coordinator. If SQLite cleanup fails after the authoritative revocation commit, report revocation as effective with cleanup pending and retry cleanup later; do not report a rollback or expose D-dependent scoring. Every scored read checks current collection permission/epoch directly (not an in-memory or SQLite pointer alone) before accepting D-dependent data; revocation therefore makes D-derived scoring unavailable immediately after the authoritative revocation commit, even if cleanup is delayed by a crash. On restart, an epoch mismatch cannot reactivate old rows. Transmission-only cancellation/revocation fences the active run and prevents subsequent sends/publication but does not itself withdraw an already valid generation permitted by cached-D-use, per the owner-note contract. Authorization expires/consumes at run end and is not required for later reuse of valid cached results. Active network cancellation is best effort; source/policy fences are mandatory.

No separate durable score/profile artifact may bypass these checks. On each scored read, validate active semantic identity and all relevant current source/eligibility identities; if invalid or SQLite is unavailable, return factual-only with not-ready/stale status. Preserve precise derived-artifact invalidation and factual-only wishlist fallback from the current references; do not broadly clear unrelated artifacts.

## Collection v9 to v10 migration and recovery

Migration removes embedded Jev pair-cache/generation payloads from collection v9 and produces collection v10 with games/notes preserved and only minimal semantic preferences/permission retained. Collection cutover and SQLite initialization are separate durable steps, not one transaction. A v10 collection with a missing, partial, corrupt, or unavailable SQLite database is a valid recovered state: readers use factual-only/not-ready, never infer on startup, and semantic activation is unavailable until a later explicit Run establishes complete current coverage. It is idempotent and conservative:

- Import a numeric pair result only if current model, rubric/question/schema/policy identity, unordered pair identity, exact relevant source provenance/fingerprints (including every sent name fingerprint), note versions, and complete sent-state dependency set can be proved from the existing record and current sources. Old v9 rows with incomplete provenance are discarded, not upgraded by guesswork.
- Otherwise discard the score rather than infer provenance or treat a cache entry as fresh. Emit a user-visible migration notice and report discarded-cache count without source text.
- Never migrate an active run as resumable authorization, never migrate permission as fresh note-transmission consent, and do not activate a generation merely because imported row counts match. Activation requires independently proving complete current required coverage and all current identities; otherwise migrate with no active semantic pointer.
- Semantic weights/settings may be retained only under the approved current collection contract; migration does not enable semantics or cached-D-use that was not already explicitly enabled.
- If SQLite is missing, corrupt, unavailable, or reset, preserve collection authority and treat every judgment as a cache miss. Do not automatically call Jev. Keep semantic scoring factual-only/not-ready until an explicit Run repopulates complete coverage.

Migration and cache initialization must be restart-safe. SQLite schema migrations are versioned separately from collection schema migration. If interrupted after JSON v10 cutover but before full cache initialization/import, restart treats SQLite as missing/partial and factual-only; it may safely retry local migration/import but may not activate on counts alone or call a provider. Database corruption handling must quarantine/reset the derived cache without rewriting or losing canonical collection data. Since provider judgments are disposable, do not invent repair values.

## Run cost and user feedback

The current default `250M` is an arbitrary maximum, not a forecast of actual usage. Do not label it estimated consumption or invent costs. Report separately: eligible/request counts, cache hits/misses, estimated remaining request count, configured hard limits, and actual provider usage after responses where returned. A characters-divided-by-four estimate is rough and incomplete: if shown at all, present only as a broad defensible token range with its limits stated, not as a precise estimate or dollar cost. Clearly distinguish estimate, quota/limit, and provider-reported actual usage. Do not promise exact cost when provider pricing/usage data is unavailable.

Show compact aggregate progress and failure details; do not force pair-by-pair inspection. The user can cancel explicitly. Cancellation prevents new submissions and fences activation; already transmitted text cannot be recalled. UI and API status expose no note contents, per-game note presence, fingerprints, or private consent values.

## Code seams

Implementation should reconcile these existing seams against current code before edits:

Cleanup is a primary implementation deliverable, not a compatibility layer to keep indefinitely. Remove obsolete collection-embedded pair judgments, generation/progress payloads, manifest delivery/acknowledgement receipts, pre-run freeze/lock machinery, and the web/CLI controls and tests built around them. Replace their call sites and tests with the SQLite cache, direct Run flow, and source-validity checks. Retain only collection-owned source, settings, permissions, and necessary durable fences; do not leave two competing cache/authorization paths.

- `packages/shared/src/validation.ts`: semantic contracts and collection v10 parsing/migration boundary; preserve pure `semanticRedundancy` input/output validation.
- `packages/daemon/src/services/semantic-redundancy-state-service.ts`: collection-owned preferences/epochs and safe projection.
- `packages/daemon/src/services/semantic-refresh-capture-service.ts`: freeze eligible source identities and compact run disclosure.
- daemon runtime/service and resolver: explicit Run, status/cancel, lazy cache lookup, source checks, validated activation/factual fallback.
- source-vector and collection-mutation services: monotonic source fences, mutation ordering, stale result rejection.
- storage service: v9-to-v10 migration and SQLite lifecycle/schema ownership.
- web redundancy page: explicit Run, compact aggregate disclosure/progress, authorization, cancellation, no mandatory pair browser.

The daemon remains the only inference and database writer boundary. Keep provider integration behind the approved daemon-owned typed-Jev capability. Do not let read handlers invoke the provider.

## Validation and staged gates

1. **Storage boundary:** migration fixtures prove conservative v9 import/discard behavior, v10 collection retains only authoritative fields/minimal preferences, no plaintext in SQLite, idempotent SQLite schema migration, and cache loss/corruption fallback without inference.
2. **Identity and invalidation:** tests cover unordered key canonicalization; source/model/rubric/question/schema changes; exact names sent; independent versus shared C and D dependencies; note version changes including identical-text set; BGG description changes invalidating shared-request D but retaining independent D-only rows; game deletion; cached-D revocation; and no stale upsert after purge or epoch advancement.
3. **Run lifecycle:** fake-provider tests prove no calls from reads/settings/note writes/startup/cache miss, stable lazy iteration, cache-hit skips, per-request pre/post checks, partial failure preservation, cancellation, restart without automatic resend, explicit rerun using valid partial cache, and full-coverage-only activation.
4. **Concurrency/crash:** interleave note edit, description refresh, eligibility/source-setting change, consent revocation, provider completion, SQLite checkpoint, activation, and process crash at every collection/SQLite boundary. Verify edits are never blocked by a pair lock; stale responses are discarded; observable results are factual-only or fully valid semantic output, never partial/stale semantic output. Verify cross-file failure recovery without asserting atomicity.
5. **Privacy and scoring:** inspect DB, logs, errors, progress/status API, and broad collection responses for absence of note/description plaintext and per-game note-state leaks. Verify D and shared C purge, C-only retention across note edits where valid, no generation resurrection across restart/A→B→A epoch changes, and unchanged pure scoring behavior with factual-only fallback.
6. **UX acceptance:** direct explicit Run; concise scope, provider/model, note-bearing count, retention caveat, budget limits versus defensible estimate; compact progress/cache hits; cancellation/failure/retry; no required full pair browsing; edits can proceed during a run and stale inputs are reported/discarded. Verify no claim of physical pair lock or exact costs unsupported by provider data.

## Explicitly open

- Exact SQLite file path, journal/synchronous settings, retention/compaction policy, and whether optional WAL recovery tooling is warranted. Choose only after checking the repository's data-directory and backup conventions; cache correctness must not depend on a particular journaling mode.
- The concrete implementation of the shared short critical section and collection-before-SQLite/read ordering. The contract is settled here: mutations/revocations, final source verification plus result upsert, and activation checks serialize; network calls do not. Do not resolve this by holding a lock over network I/O or claiming cross-file atomicity.
- Which existing v9 cache rows can actually prove complete provenance for import. Default to discard with notice when uncertain.
- Provider-reported usage fields and a defensible token-estimation methodology. If unavailable, show counts and hard limits only rather than fabricated estimates or costs.

No additional user decision is a prerequisite to parent review of this draft. The exact DB operational defaults and migration importability are implementation/review gates, not reasons to reinstate mandatory pair browsing or block pair edits.

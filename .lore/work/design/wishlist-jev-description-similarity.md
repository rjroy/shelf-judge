# Wishlist-to-owned description similarity

Approved by the owner on 2026-10-03, including the consumer and lifecycle choices described below. Proposal labels preserve the distinction from existing implemented behavior; they no longer indicate pending design approval. Implementation must reconcile the named current references before enabling this extension.

> **Owner amendment — 2026-10-03:** The owner additionally approved an explicit Jev run that by default refreshes all necessary wishlist candidate/owned C comparisons, reuses valid current C_ONLY hits, and does not infer on ordinary reads. Wishlist entries persist a compact BGG source snapshot with description and the factual scoring inputs required for offline/restart F (optional for legacy entries). A valid saved prediction remains valid and rankable when C is unavailable; cache availability does not partition or gate ranking. On acquisition, eligible current C_ONLY candidate pair results may be rekeyed to the owned game when all source, cache-contract and eligibility checks pass; do not purge/reinfer those valid judgments. This amendment is approved design authority, not delivered behavior.

> **Owner amendment — 2026-10-03 (source and result projection):** Persist the compact BGG scoring inputs needed to compute factual similarity offline/restart, not description alone. Keep the saved base prediction and factual redundancy preview intact. Expose current blended candidate redundancy as a separate read/result projection; redundancy sorting prefers that current adjustment when computable, otherwise the saved factual adjustment, otherwise the base predicted score. A missing compact scoring source means no refreshed blend (even if C exists); use saved adjustment/base prediction fallback rather than fabricating F. A computed zero-neighbor result is penalty 0 and adjusted score equal to base, not unavailable.

## Decision

Add a persisted Jev description-similarity signal for a wishlisted candidate compared with currently eligible owned games. The agreed scoring scope is wishlist-versus-eligible-owned only, using the existing similarity blend and no owner-note signal for a wishlist candidate. The agreed application scope is existing candidate ranking/fitness and strongest-owned-overlap, not a new ranking mode or algorithm.

For each candidate/owned pair, compute the existing factual score F and, when current, the cached description comparison C. Use the current semantic redundancy weights and normalize over only the positive-weight signals available for that pair:

`(wF * F + wC * C + wO * O) / (sum of weights for available signals)`

Here **F** is factual similarity, **C** is description similarity, and **O** is owner-note similarity. Existing code/settings spell the weights `factual`, `description`, and `ownerNote`; existing Jev cache labels **C = description** and **D = owner-note**. In this wishlist design, **O = owner-note** in the formula and no candidate-side O value exists, so omit O entirely from numerator and denominator. Never consume cache D or any shared-request C judgment whose dependency includes notes. Missing, stale, disabled, or failed signals are omitted; a valid score of zero is included. No pair-coverage gate is needed: each pair falls back independently to permitted current signals, including factual-only.

Existing wishlist predictions and sorting remain valid independently of semantic-cache state. Keep `predictedScore` as the existing prediction result and predicted-score sorting unchanged; do not exclude, partition, or demote an entry because its C comparison is missing, stale, or unavailable. The blend informs the candidate redundancy/overlap result. Do not require a fresh prediction to rank a valid saved prediction.

The wishlist prediction, breakdown, niche impact, and factual-only redundancy preview remain their saved snapshots until the existing explicit single/bulk factual Refresh replaces the documented fields in place, preserving entry ID and `addedAt`. Adding another item, explicit Jev comparisons/cache updates, and unrelated source changes do not silently rewrite these fields. Current C comparisons are persisted separately in Jev SQLite and feed a separate current candidate-to-owned redundancy/overlap result. The conceptual read projection exposes which redundancy adjustment is current-blended, saved factual fallback, or base-score fallback; exact route/field names are implementation detail. Redundancy sorting/display uses current adjustment when computable, otherwise saved `redundancyPreview.adjustedScore`, otherwise `predictedScore`. Current adjustment always uses saved base `predictedScore` and its resulting `adjustedScore` once; it never replaces the persisted base or subtracts a second penalty. Missing C falls back to available F and does not invalidate or partition the saved prediction. This preserves REQ-WISH-4/11 snapshots without a cache-availability ordering partition.

## Inputs, identity, and eligibility

### Candidate source hydration

Current state: `WishlistEntry` contains BGG ID and snapshot name but no description or scoring-field source; wishlist persistence is raw JSON parse plus atomic write. `predictBggGame` fetches scoring input and currently makes a transient `Game` with `bggData.description: null`. The parser for a BGG Thing returns nullable description and `fetchedAt`; there is no reusable wishlist candidate source in current code. The existing `name` field is the candidate's saved BGG name and `bggId` its identity.

**Approved compact scoring-source extension:** persist an optional-for-legacy BGG source snapshot with each new/refreshed wishlist entry; existing `bggId` and `name` are its BGG identity/name. Do not persist a full `Game`/`BggGameData`. Its minimal factual fields, projected from current `BggGameData`/`Game`, are:

| Persisted source input | Encoder use |
| --- | --- |
| description: `string | null` | Jev C source; null/empty/whitespace is unavailable under current `hasDescription` rule |
| mechanics and categories as arrays of names | Binary vocabulary/membership (`feature-vector.ts:56-69, 164-171`) |
| weight and community rating as `number | null` | Continuous vector fixed normalization to `[1,5]` and `[1,10]` (`feature-vector.ts:182-195`) |
| minPlayers, maxPlayers, bestPlayers, playingTime as `number | null` | Continuous vector normalized by current observed source ranges (`feature-vector.ts:109-143, 189-195`) |
| one valid `observedAt` timestamp | Identifies the BGG Thing observation for those fields |

The intended compact contract is one optional-for-legacy source object, not a set of unrelated partial fields:

```ts
interface WishlistBggSourceSnapshot {
  observedAt: string;
  description: string | null;
  mechanics: string[];
  categories: string[];
  weight: number | null;
  communityRating: number | null;
  minPlayers: number | null;
  maxPlayers: number | null;
  bestPlayers: number | null;
  playingTime: number | null;
}

// WishlistEntry: bggSource?: WishlistBggSourceSnapshot
```

`WishlistEntry.name` and `bggId` are from the same verified BGG Thing observation identified by `bggSource.observedAt`; do not duplicate the full name/identity inside the object. An absent object identifies a legacy entry without any established compact source. On add/refresh, persist the complete projected object only after a successful matching BGG Thing response.

Mechanics/categories need only names because the existing encoder uses names, not BGG IDs. Ratings, axes, image/thumbnail, year, full Thing data and other `Game` fields are not needed for this factual vector. Null numeric inputs retain the existing `encodeGame` fallback behavior; do not invent replacement values in storage. Source object absent means legacy/unobserved; within an observed source, null description means BGG supplied no usable prose and empty arrays/null numeric inputs are the exact parsed observation used by current encoder defaults. Preserve description exactly, without trimming, for `fingerprintJevSource`.

### Factual encoding and normalization

The compact source is sufficient to construct the candidate factual `Game` projection without persisting a full `Game`. At each current comparison, rebuild factual context from the coherent current owned-side/collection source capture, not from cached candidate vectors or wishlist-time ranges. Match existing preview behavior: `redundancy-preview.ts:30-33` builds feature vocabulary and continuous ranges from `collection.games` with BGG data; `redundancy-factual.ts:17-19` uses that source universe, which can include collection games not eligible as neighbors. This is the current scorer's normalization universe; the candidate pair set itself remains only candidate versus eligible owned games. Encode candidate mechanics/categories against that current vocabulary and continuous values against ranges observed from the current collection source. Existing fixed weight/community-rating normalization and null fallbacks in `encodeGame` remain unchanged. Thus changes to current collection composition may change F, but a restart does not require refetching wishlist candidate BGG fields or a fresh prediction.

Populate the compact scoring source on wishlist add and explicit single/bulk factual/source refresh from one actual, verified BGG Thing observation. The saved `name` must come from that same observation and match the existing `bggId`; timestamp covers the whole compact source. A successful source refresh replaces source fields while preserving existing prediction refresh semantics. On BGG fetch/parse failure, follow current refresh failure behavior: do not overwrite the prior entry snapshot with missing or partial source (bulk refresh already leaves failed entries unchanged). For legacy entries without the source, explicit factual refresh or explicit Jev run may hydrate BGG data and persist it. Ordinary reads use persisted source, including after restart/offline; no BGG hydration prerequisite. This is a bounded approved source-data exception; Jev rows and logs still contain no raw source text. Source fingerprints derive from exact persisted description with existing SHA-256 fingerprinting. Newly observed changes fence/invalidate matching candidate comparisons. No model knowledge may substitute for absent BGG description.

Owned-side inputs come from one coherent current daemon source capture, not the wishlist's saved snapshot. Eligible owned games are exactly the live redundancy scoring set: owned collection games with a non-null, positive, non-vetoed score. Exclude previously-owned games, wishlist candidates, unscored/vetoed games, and every other transient search result. Reuse existing eligibility capture and scoring paths rather than defining a broader candidate-specific ownership rule. The candidate itself is never inserted into the collection or owned universe.

### Cache identity and safe reuse

Store candidate comparisons in the existing daemon-owned Jev SQLite pair cache, with a stable, namespaced candidate identity derived from collection ID and BGG ID so it cannot collide with a real local game ID. Cache the C signal only. Each dependency records candidate BGG identity, both member names, and exact description fingerprints; it records no description text, note fingerprint, note version, note content, or candidate local game ID. Use existing pinned model and question/rubric/schema/score-mapping version provenance. A value is reusable only when persisted candidate and owned source identities, both current source fingerprints, and current cache provenance/contract/policy match. Candidate source authority after restart comes from the persisted wishlist compact source, not a Jev row. Continue canonical unordered pair ordering.

This cache row is not an owned-game row and must not make a wishlist item eligible for collection fitness, collection-wide coverage counts, or owned-pair progress. The cache/read layer must explicitly distinguish candidate-to-owned rows from collection rows (through a safe namespace/identity contract or equivalent validated discriminator) so a candidate comparison cannot be consumed as a collection pair. Do not silently infer a new schema field or API: select and document the minimal compatible representation during implementation; if current cache identity constraints cannot safely represent this distinction, resolve the cache schema change before enabling writes.

Candidate comparison contains descriptions only. It is a C_ONLY request: request state contains no `owner_note` field or other note-derived state, and it does not require or read cached-D permission / owner-note transmission authorization. Existing collection C requests that share state with notes remain note-dependent and must not be reused as candidate C. The current collection cache validator accepts a C_ONLY row only when it validates against current names/descriptions, model/rubric/question/schema/score-mapping/policy contract and collection ID; the note-use permission check applies only to note-dependent rows (`jev-pair-read-proof.ts:127-198`). Candidate-derived C must meet that same C_ONLY contract before collection-side reuse. A candidate cache hit does not require transmitting notes.

## Scoring and consumers

Use the candidate's existing valid saved prediction as the base for wishlist ranking; Jev cache availability does not change prediction validity or ordering eligibility. Current candidate prediction may be refreshed only by existing explicit wishlist Refresh semantics, not as a prerequisite to a Jev run. Existing preview contracts store base prediction and `RedundancyAdjustment` separately: Search displays the adjustment's already-computed `adjustedScore`, and Wishlist redundancy sort uses `redundancyPreview.adjustedScore` rather than subtracting `penalty` itself. The approved comparison supplies blended per-pair similarity to that same adjustment calculation; use saved `predictedScore` as the base when a fresh prediction was not requested, then consume `adjustedScore` once. Never alter saved `predictedScore` because a semantic cache hit/miss occurred, nor apply the penalty again to `adjustedScore`. Candidate F uses the compact factual source and current owned collection normalization; add valid C when current and positive-weight. Preserve blend arithmetic, threshold and `[0,1]` semantics, with no candidate-specific weights. With only F available, use F alone; unavailable C is omitted from the denominator. A candidate source object absent on a legacy entry means no refreshed blend, even if a C cache row exists: do not fabricate F from description or cached result. Fall back to saved factual redundancy adjustment, then saved base prediction. With an established source and a computable pair set, a zero-neighbor result is a valid zero-penalty adjustment whose `adjustedScore` equals the saved base prediction; it is not an unavailable result.

Candidate ranking/fitness and strongest-owned-overlap consume the same F/C per-pair blend through existing candidate redundancy semantics; this does not reorder or invalidate a saved base prediction based on cache coverage. Candidate adjustment is prospective only and never changes owned penalties. No candidate is added to comparisons for other candidates. Strongest-overlap selects the owned neighbor with the highest available blend; no confidence weighting or separate model explanation. Critically, `computeRedundancyAnalysis` validates a complete factual pair universe for supplied eligible collection IDs (`redundancy-engine.ts:90-146, 202-260`). Do not pass candidate-only pairs as that complete collection table: the candidate path must reuse the existing blend and neighbor/penalty arithmetic for candidate-to-owned pairs without claiming owned-owned rows were computed. It must not trigger owned-owned inference, require owned-owned semantic coverage, or alter owned-game penalties. If no C is usable, ordinary F fallback remains; if no pair signal is available, omit that pair's redundancy effect without suppressing the base prediction or its rankability.

Report comparison freshness/availability honestly using existing factual/not-ready/stale/partial/ready vocabulary where it fits. A pair can be factual-only while another is F+C; do not claim complete coverage as a prerequisite. Provider/cache failures degrade per pair to available F, never block wishlist display or make a valid zero disappear. Jev does not change the prediction calculation itself; it informs the existing candidate redundancy adjustment/overlap once. A valid saved base prediction remains available to existing ranking when semantic comparisons are absent or cache unavailable.

### Current result and redundancy-sort fallback

Keep the durable `WishlistEntry` snapshot untouched by Jev reads/runs. Return the current candidate comparison and `RedundancyAdjustment` as a distinct read/result projection alongside the existing entry, with provenance sufficient to distinguish current blended calculation from saved factual `redundancyPreview` and base `predictedScore`; no particular operation or JSON field names are specified here. The redundancy ordering/display precedence is deterministic:

1. If the compact scoring source exists and the current candidate-to-owned pair calculations are computable, use the current blended `RedundancyAdjustment.adjustedScore`.
2. Otherwise, if a saved factual `redundancyPreview.adjustedScore` exists, use that saved adjustment.
3. Otherwise use the saved base `predictedScore` (or existing no-prediction placement when it is null).

The predicted-score sort continues to use `predictedScore` itself and is never partitioned by C availability. A missing/stale C row does not make the current adjustment unavailable when F can be computed from compact factual source; use F-only normalization. If neither a usable comparison blend nor compact factual source can produce a current adjustment, take the fallback above; do not fabricate F from description/C and do not invalidate the saved base prediction. If current calculation succeeds but yields no niche neighbors (or no better neighbor), return a valid adjustment with penalty `0`, `adjustedScore` equal to `predictedScore`, and an empty/appropriate neighbor list. That current zero-penalty result takes precedence over an older saved factual adjustment. This projection changes neither saved `predictedScore` nor saved `redundancyPreview`.

## Lifecycle and execution

### Explicit operation and scheduling

Use the established daemon-owned Jev run/refresh controls, typed-Jev gateway, disclosure and progress/cancellation conventions. **Default explicit wishlist run scope is all wishlist entries and all eligible-owned comparisons that need C work**, reusing every current valid C_ONLY cache hit and requesting only missing/stale comparisons where both descriptions are usable. An explicitly selected smaller candidate scope is also allowed. Each submitted pair must be covered by the run disclosure/authorization; no Jev inference occurs on ordinary reads, sorting, add, or factual refresh. For a legacy entry without the compact scoring source, an explicit factual/source refresh or the explicit Jev run may fetch and persist BGG Thing source. The run's pair disclosure/authorization covers only actual Jev submissions under existing controls; BGG source hydration is not Jev inference. Ordinary reads use persisted wishlist source only and require no BGG remote hydration. Preserve current run limits, budgets, progress and cancellation conventions.

The existing collection Jev Run authorizes its disclosed collection scope; it does not automatically authorize wishlist candidate descriptions. Candidate scope and pair counts must be included in the explicit candidate-run disclosure, with the same provider/model, transmission, possible retention, budget, and cancellation facts used by current Jev controls. Description-only candidate comparisons need no owner-note consent, but do require explicit authorization for the additional candidate/owned description pairs. A later refresh needs the established fresh authorization behavior. Exact route/operation names and client controls are implementation details, not defined here.

### Source freshness and in-flight fences

At request admission capture a coherent owned collection/prediction/settings source and wishlist entry including BGG ID/name, complete compact scoring source and observation time. Before sending each pair, verify the candidate remains the same wishlist entry/source, has not become owned, and its saved BGG source is unchanged; verify owned eligibility and descriptions too. After provider response, recheck these identities plus authorization, policy and model/rubric versions before upserting. Wishlist removal, source refresh, acquisition or entry replacement fences late results; stale/canceled responses cannot be reinserted. Recheck the current wishlist entry/source at final cache publication, serialized with wishlist mutations using the existing daemon mutation boundary; do not hold locks across inference. Read-time reuse after restart validates against persisted candidate source/name/identity; no BGG fetch is needed for an entry with established source fields. Fingerprint changes on observed BGG refresh invalidate C. Do not promise detection of remote changes absent a new BGG observation.

Revalidate candidate rows against persisted candidate description/name/identity, both owned-side sources, eligible-owned membership, and actual cache contract/provenance. Mismatch makes C unusable for that pair; use F if the compact factual source exists. Existing owned pair invalidation must not be broadened to purge unrelated candidate rows. Candidate source completeness, description/name, BGG identity/observation, owned eligibility/scores, factual weights, effective semantic weights/policy and question/model/source identity that affect the result must be encoded or checked through the existing collection cache validation contract. C_ONLY rows need no note-use permission; D and SHARED_CD rows are never candidate inputs. The base saved prediction remains rankable when any comparison signal is unusable.

### Removal, acquisition, and retention

Wishlist removal/clear purges candidate rows for that BGG identity and fences in-flight responses. **Acquisition is different:** when a wishlisted game is added to the collection, the existing add-game flow removes its wishlist entry (REQ-WISH-10), and compatible C_ONLY candidate pair results must be transferred/rekeyed to the corresponding owned-game pair rather than purged and reinferred. Reuse is allowed only when the acquired game's current BGG ID, name and exact description fingerprints match the candidate-side dependencies; the other owned member also matches current name/description fingerprints; it is currently eligible for collection scoring; the row's collection ID and provenance (model, rubric, question, request schema, score mapping, semantic policy) pass the existing cache validator; the semantic description signal is enabled/usable; and the row is C with dependency kind C_ONLY. Preserve its numeric value, original completion time and original provenance while changing only pair identity and dependency member ID as necessary. Do not transfer D_ONLY or SHARED_CD, any note-dependent C, stale/invalid rows, or rows failing any check. Existing collection reads can consume validated C_ONLY rows without owner-note-use permission; their validator applies note-use permission only to note-dependent rows (`jev-pair-read-proof.ts:145-198`).

This transfer is cache rekey/reuse, not inference. Serialize acquisition, wishlist removal, cache rekey and source-fence update so in-flight candidate responses cannot recreate a removed candidate row or overwrite a transferred row. If exact transfer cannot be proven, the row is not reusable; normal explicit run may recompute it under owned identity. Do not apply wishlist-removal purge policy to acquisition.

Keep candidate judgments only while wishlist membership/source and row provenance remain valid; stale rows are unusable immediately and may be cleaned up. Removal purges; acquisition transfers only provably valid C_ONLY rows as above. Wishlist JSON is the authoritative local candidate BGG source (description plus factual encoding inputs); Jev SQLite stores only fingerprints and numeric judgments, never raw source text, model explanations, prompts, note data, or owner-note-dependent result for candidate pairs. Jev cache loss makes C unavailable and falls back per pair to F when compact source exists; it does not invalidate the saved prediction. Persisting this source in wishlist JSON is an approved source-data exception, not a Jev cache exception.

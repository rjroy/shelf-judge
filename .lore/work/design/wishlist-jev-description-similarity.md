# Wishlist-to-owned description similarity

Approved by the owner on 2026-10-03, including the consumer and lifecycle choices described below. Proposal labels preserve the distinction from existing implemented behavior; they no longer indicate pending design approval. Implementation must reconcile the named current references before enabling this extension.

## Decision

Add a persisted Jev description-similarity signal for a wishlisted candidate compared with currently eligible owned games. The agreed scoring scope is wishlist-versus-eligible-owned only, using the existing similarity blend and no owner-note signal for a wishlist candidate. The agreed application scope is existing candidate ranking/fitness and strongest-owned-overlap, not a new ranking mode or algorithm. Whether those consumer results are served as live comparisons alongside preserved snapshots is a separate proposal below.

For each candidate/owned pair, compute the existing factual score F and, when current, the cached description comparison C. Use the current semantic redundancy weights and normalize over only the positive-weight signals available for that pair:

`(wF * F + wC * C + wO * O) / (sum of weights for available signals)`

Here **F** is factual similarity, **C** is description similarity, and **O** is owner-note similarity. Existing code/settings spell the weights `factual`, `description`, and `ownerNote`; existing Jev cache labels **C = description** and **D = owner-note**. In this wishlist design, **O = owner-note** in the formula and no candidate-side O value exists, so omit O entirely from numerator and denominator. Never consume cache D or any shared-request C judgment whose dependency includes notes. Missing, stale, disabled, or failed signals are omitted; a valid score of zero is included. No pair-coverage gate is needed: each pair falls back independently to permitted current signals, including factual-only.

**Proposed consumer/lifecycle choice:** use the candidate/owned signal in a live comparison result for candidate fitness/ranking and strongest-owned-overlap, without rewriting the wishlist entry. This live-result/snapshot separation is not part of the agreed scoring scope; it is proposed to fit the existing snapshot contract. A saved wishlist entry remains historical: its predicted score, prediction breakdown, niche impact, and factual-only redundancy preview stay as saved until the existing explicit single/bulk factual Refresh replaces those fields in place, preserving entry ID and `addedAt`. Adding another item, semantic comparisons/cache changes, and source changes do not rewrite snapshots. The live result uses current inputs; when unavailable, show the historical snapshot explicitly as historical with live comparison unavailable rather than substituting it as current.

## Inputs, identity, and eligibility

### Candidate source hydration

The wishlist record is not a sufficient Jev input and remains compact. **Proposed source rule:** every live candidate comparison first resolves candidate input from the latest locally observed BGG data available through the existing BGG data path/cache, according to that path's freshness policy. It may hydrate/read BGG data, but this is not a Jev request. Existing owned-game `bggData` is persisted with owned games; the inspected candidate `predictBggGame` path fetches scoring input and currently leaves candidate description null, and no durable candidate BGG description cache was found. Therefore implementation must either use a suitable existing locally observed BGG data source if available or explicitly fetch/parse current BGG Thing data through the BGG client and retain it only in memory for that comparison; it must not claim the repository already has a candidate description cache. Record/retain its observation identity/time for comparison fencing. “Current” means latest locally observed under the actual BGG cache/freshness policy, not guaranteed latest remote BGG state. Do not claim remote freshness that cannot be observed.

Do not copy the full fetched game or description into `wishlist.json`, Collection, a new permanent game record, Jev rows, prompt logs, or other derived durable records. The existing BGG data cache/storage may retain description under its own contract, but Jev cache stores only fingerprints and provenance. If candidate BGG source cannot be established, C is unavailable. If F inputs can still be established from current local data, use F-only; otherwise do not report a live ranking/comparison and retain only a clearly labeled historical snapshot with live result unavailable. Ordinary wishlist list/add/prediction/factual refresh must not call Jev.

Owned-side inputs come from one coherent current daemon source capture, not the wishlist's saved snapshot. Eligible owned games are exactly the live redundancy scoring set: owned collection games with a non-null, positive, non-vetoed score. Exclude previously-owned games, wishlist candidates, unscored/vetoed games, and every other transient search result. Reuse existing eligibility capture and scoring paths rather than defining a broader candidate-specific ownership rule. The candidate itself is never inserted into the collection or owned universe.

### Cache identity and safe reuse

Store candidate comparisons in the existing daemon-owned Jev SQLite pair cache, with a stable, namespaced candidate identity derived from collection ID and BGG ID so it cannot collide with a real local game ID. Cache the C signal only. Each dependency records candidate BGG identity, both member names, and exact description fingerprints; it records no description text, note fingerprint, note version, note content, or candidate local game ID. Use existing pinned model and question/rubric/schema/score-mapping version provenance. A value is reusable only when read-time candidate source has been established from current/local BGG data (including after restart), both current source fingerprints and all current model/policy/version/authorization requirements match. A cache row by itself does not establish candidate source authority. Continue canonical unordered pair ordering.

This cache row is not an owned-game row and must not make a wishlist item eligible for collection fitness, collection-wide coverage counts, or owned-pair progress. The cache/read layer must explicitly distinguish candidate-to-owned rows from collection rows (through a safe namespace/identity contract or equivalent validated discriminator) so a candidate comparison cannot be consumed as a collection pair. Do not silently infer a new schema field or API: select and document the minimal compatible representation during implementation; if current cache identity constraints cannot safely represent this distinction, resolve the cache schema change before enabling writes.

Candidate comparison contains descriptions only. It is a C_ONLY request: request state contains no `owner_note` field or other note-derived state, and it does not require or read cached-D permission / owner-note transmission authorization. Existing collection C requests that share state with notes remain note-dependent and must not be reused as candidate C. A candidate cache hit does not require transmitting notes, and a failure or revocation in owner-note processing cannot expose or invalidate note data that was never part of the candidate request.

## Scoring and consumers

**Proposed live scoring inputs:** compute a fresh candidate prediction using the same current prediction settings/source capture and eligible owned-game scores used for its comparison. Do not use `WishlistEntry.predictedScore` as the candidate's live score. If prediction is unavailable, do not fabricate a live fitness ranking or candidate penalty; the historical saved snapshot may still be shown as history. Candidate factual pair F can be computed only when current candidate/owned feature inputs are established; if they are not, omit F. For the candidate and each eligible owned game, produce F through the same feature encoder/settings used by the existing redundancy scorer, then add a current valid C judgment if available and positively weighted. Existing blend arithmetic and threshold meaning remain authoritative. Preserve `[0,1]` and factual binary/continuous weighting; do not use another cosine or candidate-specific weights. With F and C configured positive but only F available, use F alone; with F weight zero and C missing, that pair has no usable score. When all signals are unavailable, omit that pair.

**Proposed consumers:** if approved, candidate fitness/ranking and strongest-owned-overlap consume the same F/C per-pair blend. Candidate adjustment uses existing niche-neighbor and penalty semantics against the eligible owned set; it is prospective only, never changes owned penalties. No candidate is added to comparisons for other candidates. Strongest-overlap selects the owned neighbor with the highest available blend; no confidence weighting or separate model explanation. Critically, `computeRedundancyAnalysis` validates a complete factual pair universe for the supplied eligible collection IDs (`redundancy-engine.ts:90-146, 202-260`). Do not pass candidate-only pairs as if they were that complete collection table: the candidate path needs a boundary that reuses the existing blend and neighbor/penalty arithmetic for candidate-to-owned pairs without pretending owned-owned rows were computed. It must not trigger owned-owned inference, require owned-owned semantic coverage, or alter owned-game penalties. If no pair has a usable blend, no live semantic overlap/adjustment is returned; factual-only behavior applies where F is established.

Report comparison freshness/availability honestly using existing factual/not-ready/stale/partial/ready vocabulary where it fits. A pair can be factual-only while another is F+C; do not claim complete coverage as a prerequisite. Provider/cache failures degrade per pair to available F, never block ordinary wishlist display or make a valid zero disappear. Jev does not change prediction itself; it informs the existing redundancy adjustment/ranking contribution only.

## Lifecycle and execution

### Explicit operation and scheduling

**Proposed execution choice:** use established daemon-owned Jev run/refresh controls, typed-Jev gateway, disclosure and progress/cancellation conventions. Extend scope with explicitly selected wishlist candidate(s) compared only with eligible owned games. Ordinary comparison reads may hydrate candidate data through BGG path/cache, but never call Jev; wishlist add and existing factual refresh likewise remain Jev-free. A client may explicitly request candidate inference; daemon captures, authorizes, schedules, fences and stores it. Preserve existing limits, budget, progress, and cancellation conventions. No implicit full wishlist-by-owned precomputation. Execution controls are a proposal, not agreed scoring scope.

The existing collection Jev Run authorizes its disclosed collection scope; it does not automatically authorize wishlist candidate descriptions. Candidate scope and pair counts must be included in the explicit candidate-run disclosure, with the same provider/model, transmission, possible retention, budget, and cancellation facts used by current Jev controls. Description-only candidate comparisons need no owner-note consent, but do require explicit authorization for the additional candidate/owned description pairs. A later refresh needs the established fresh authorization behavior. Exact route/operation names and client controls are implementation details, not defined here.

### Source freshness and in-flight fences

At request admission capture a coherent current owned collection, prediction/settings state, factual weights and established candidate BGG source with observation identity/time. Before sending each pair, verify the candidate remains in requested wishlist scope, has not become owned, and its BGG identity and observed description source are unchanged; verify owned eligibility and descriptions too. After provider response, recheck these identities plus authorization, policy and model/rubric versions before upserting. Stale/canceled results are discarded even if provider cancellation failed. Use existing source coordinator/freshness fences and short critical sections, never locks across inference. Read-time reuse after restart first re-establishes candidate source from the existing local BGG data/cache path or an allowed BGG hydration; if it cannot, do not trust a fingerprint alone to serve C. Fingerprint changes on observed BGG updates invalidate C. Do not promise detection of remote changes absent a new BGG observation.

Revalidate on reads too. Source or scoring-policy mismatch makes only the affected candidate signal unusable; ordinary reads fall back to current F if candidate/owned factual inputs are established. Otherwise return no live result and keep the historical snapshot labeled historical. Existing owned pair invalidation must not be broadened to purge unrelated candidate rows. Description, name, candidate BGG identity/observation, owned eligibility/scores, factual weights, effective semantic weights/policy, and question/model/source identity that affect the result must be encoded in identity or checked by scorer. Use dependency-specific invalidation where possible.

### Removal, acquisition, and retention (proposed)

Wishlist removal/clear purges candidate rows for the removed BGG identity; purge is safe even though fingerprint validation would already prevent reuse. If a wishlisted candidate is acquired, the existing add-game flow removes its wishlist entry (REQ-WISH-10); candidate pair rows are purged as part of or immediately fenced by that transition. The newly owned game participates in collection scoring under ordinary collection cache rules, not by reinterpreting candidate rows. If acquisition and purge cannot be coordinated atomically across wishlist and Jev SQLite, persist or derive a monotonic candidate invalidation fence before success becomes visible, so a late result cannot recreate usable candidate data.

**Proposed retention choice:** keep candidate judgments only while wishlist membership, dependencies and policy remain valid; stale rows may be asynchronously purged but are unusable immediately. Purge rows on permanent removal/acquisition, with a fence preventing late repopulation. Do not persist candidate source text/descriptions in Jev cache. Existing BGG cache/storage may retain BGG source under its own current contract. Jev cache loss means C unavailable and factual fallback where inputs establish F; otherwise no live result. Never persist model explanations, prompts, note data, or live semantic candidate values in historical wishlist JSON.

## Decision

Approved scope is the wishlist-to-eligible-owned signal, existing F/C/O blend with no candidate O, existing candidate fitness/ranking and strongest-owned-overlap use, pairwise fallback, and no coverage gate.

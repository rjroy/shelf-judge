# Implementation notes: SQLite Jev pair cache

## Authority and current state

Execution checklist for the approved [design](../design/sqlite-jev-pair-cache.md). The maintained [redundancy](../../reference/specs/fitness/redundancy-scoring.md) and [owner-note](../../reference/specs/current/owner-game-notes.md) references remain authoritative for their contracts. The old Jev design/plan are historical where superseded: no collection-embedded pair cache, full pair-manifest browse/acknowledgement, pre-run freeze/lock, or pair-by-pair review. Cache/run state belongs to daemon-owned SQLite; collection JSON owns canonical games/notes, semantic preferences, cached-D permission, and durable fences.

**Phase 1 is complete; Phases 2–5 remain pending.** This is not production cutover or authorization for provider transmission. Use fakes only; no live provider calls or user data. Edits remain allowed during runs; source checks and stale-result discard, not physical pair locks, provide safety. The parent owns holistic obligation reconciliation and subsequent gates.

## Resumable phase checklist

- [x] **Phase 1 — SQLite derived numeric cache repository + unit tests.** Implement the daemon-owned SQLite lifecycle/schema, canonical unordered pair identity, versioned per-signal numeric judgment/provenance records, bounded run/progress and advisory activation storage, and repository-level unit tests. Do not cut production reads or writes over yet; this phase alone does not make the feature ready. Tests use synthetic fixtures and injected dependencies.
- [ ] **Phase 2 — Collection v10 migration and cutover.** Migrate v9 to v10 retaining games/notes and only approved semantic preferences/permission/fences; conservatively import only provable rows, otherwise discard with a safe notice/count. Cut reads/writes to SQLite, wire resolver and targeted mutation/purge ordering, fail-closed recovery/corruption behavior, and remove old embedded pair/generation/progress state. No inference on startup or migration.
- [x] **Phase 2a — Temporary legacy-inference quarantine (accepted; Phase 2 remains pending).** Disable the old inference path until the v10/Run implementation is ready; missing inference is unavailable/503, and persisted legacy profiles must recompute to factual/not-ready rather than bypass the quarantine. This does not complete migration or cutover.
- [x] **Phase 2b — Exact pair identity and SQLite invalidation foundation (accepted; Phase 2 remains pending).** Establish exact per-pair/source identity and targeted SQLite signal-purge behavior. This is groundwork only: no production cache cutover or v10 activation.
- [x] **Phase 2c — Strict inactive v10 schema and pure migration (accepted; Phase 2 remains pending).** Add strict v10 schema validation and a pure v9→v10 migration while keeping the v10 alias inactive (still v9); conservatively discard old v9 cache rows that cannot be proven safe. This does not cut production reads or writes over.
- [x] **Phase 2d1 — V9-compatible legacy runtime deletion (accepted; Phase 2 remains pending).** Remove obsolete legacy runtime wiring and old-only implementation/tests while remaining compatible with v9. Obsolete endpoints return interim 503; preserve settings, factual scoring, and the existing resolver. Keep v10 inactive; no provider calls.
- [ ] **Phase 3 — Direct Run daemon runtime/authorization.** Implement explicit disclosed Run, one-execution note authorization, status/cancel, lazy all-pairs iteration, typed-Jev boundary, pre-send/post-response checks, complete-coverage activation, and safe per-pair coordination. Remove manifest/acknowledgement/freeze/lock code and routes, not retain a compatibility path. No provider calls in reads, settings, mutation, cache misses, startup, or background work.
- [ ] **Phase 4 — Web + CLI direct Run and honest budget UI.** Connect both clients to direct Run/status/cancel and safe aggregate contracts; distinguish hard limits, estimates (only if defensible), and provider-reported usage. No full-pair browser or exact-cost claims. **Designer owns web UX** and its acceptance evidence; CLI owner covers command behavior/parity.
- [ ] **Phase 5 — Cross-consumer integration/privacy/race/regression and final gates/review.** Verify daemon resolver, scored reads, web, CLI, settings, mutation, storage, and provider-boundary contracts together; prove privacy, concurrency/crash recovery, complete coverage and no stale resurrection; run assigned final gates and reconcile evidence. Parent performs holistic obligation reconciliation and release/readiness decision.

## Evidence and ownership rules

- Each phase agent owns its focused automated tests and records executable commands/results with the handoff; do not claim a requirement based on design text alone.
- An independent `bun-typescript-reviewer` reviews every completed implementation phase. Review does not replace tests.
- Web interaction, presentation and browser UX acceptance belong to the designer; this note assigns no UX design work to implementation agents.
- The parent validates this obligation map before implementation, then owns holistic reconciliation of sources, privacy, races, coverage, scoring and final gate evidence. A phase is not complete merely because its files/tests exist.
- No live provider calls, owner-note transmission, or owner-data fixtures. Provider behavior is exercised only through deterministic fakes.
- Do not mark semantic redundancy ready, enabled, migrated, or delivered until all required implementation and validation obligations pass; Phase 1 cache repository completion alone is explicitly not feature readiness.

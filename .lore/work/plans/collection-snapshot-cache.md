# Implementation plan for cached Collection snapshots

## Goal and authorization

Make repeated Collection navigation/reloads cheap when its inputs have not changed, and make an invalidating post-edit refresh materially faster than the measured ~3-second baseline. Preserve ordinary/predicted score alternatives, niche positions, utilization sorting, capacity, filters, ownership, navigation, and degraded optional features. The user approved a client-loaded initial table and requested persistence across full browser reloads. Use IndexedDB for the compact validated snapshot, not `localStorage` for the multi-megabyte body. Keep the existing “Loading your games…” presentation during validation. **This is a plan for review, not authorization to implement.** Work on branch `perf/collection-snapshot-cache`; never edit `~/Applications` or test mutations on the original data directory.

Baseline on a disposable complete copy of the real 200-game dataset: production `/collection` delivered 12,433,433 uncompressed HTML bytes in ~2.7–3.0 seconds; standard, predicted, and niche game API responses were ~3.29, 3.31, and 4.06 MB. These are point measurements, not benchmark thresholds. The existing `packages/web/app/collection/loading.tsx` already provides route-level loading UI, but the current async server page still embeds all three arrays into RSC.

## Decisions and boundaries

- Do not replace three distinct score results with one arbitrarily chosen score. Share only score-independent fields. Each ordinary/predicted alternative retains its own score, display score, and purchase-utilization values. Niche positions can be projected by game ID rather than duplicating complete niche rows. Preserve ownership and `dimensions=missing` semantics, including previously-owned counts and owned-only niche scope.
- A durable revision belongs atomically in each separately stored source it versions: collection already has one; add/migrate revisions for tournament, prediction settings, niche settings, redundancy settings, and shelf configuration, or a verified equivalent source identity for any format that cannot safely carry one. Advance only on committed changes, not failed writes/no-ops. The daemon hydrates the source vector once and serializes relevant commits and snapshot publication. Initial scope excludes external file edits while running; restart reloads all durable revisions. Include data/collection identity and representation/algorithm version in validators. Time-based BGG staleness requires expiry/rollover even without a write.
- An unchanged conditional request must return 304 without recomputing the snapshot or returning the body. A relevant edit necessarily invalidates some work; the shared compact assembly addresses that edit's latency. Required collection, axes, and tournament **scoring source** failures give a clear error with retry and no fabricated score; optional stats-display, prediction, niche, settings, or capacity failures produce a partial, non-cacheable 200 response without ETag and are retried on the next request. No stale persisted snapshot is silently presented as current when revalidation fails.
- The initial document becomes a shell plus client-loaded table. Update the maintained Collection filter/sort spec's obsolete server-fetch requirements while retaining client-side sort/filter behavior and the existing loading copy. The user also approved reconciling shelf-capacity REQ-SHELF-25 and niche-display REQ-NICHE-33 so their Collection snapshot results may be cached under complete source-revision validation; preserve standalone endpoint behavior and current-input semantics. A no-JavaScript explanation or explicit failure state is preferable to an indefinitely busy shell. The user approved this plan and the additional spec reconciliation before implementation.
- Browser persistence is deliberately limited to the compact table snapshot, scoped by server/collection identity and representation version. Keep **one stored Collection snapshot per browser origin total**: on successful validation of a different server/collection identity, replace the old identity's entry. IndexedDB failure/quota is a cache miss, not a broken page. Only validated current data is rendered. The list projection must exclude all owner-note fields including metadata.

## Step 1: Reproducible measurement and contract inventory

**Files:** add focused performance harness under `packages/web/e2e/` or a bounded script/test location; inspect `packages/web/app/collection/page.tsx`, `components/collection-table.tsx`, `packages/daemon/src/routes/games.ts`, `services/displayed-fitness-service.ts`, `services/purchase-utilization-service.ts`.

Record production-build cold load, warm unchanged navigation, full reload, and one safe edit on a **temporary copy** of `SHELF_JUDGE_DIR`; do not print private game or owner-note data into committed artifacts. Time each daemon computation and page/request boundary, record uncompressed/compressed bytes, and separate renderer time from network/server time. Record request attempt/outcome and cache hit/miss reason at service boundaries, not per game. Map data fields consumed by table sorting, filtering, predictions, niches, capacity, and navigation before trimming payload. Preserve a deterministic fixture benchmark for CI and document the real-data comparison as local evidence without storing personal data.

**Gate:** measurements are repeatable enough to compare before/after with identical data/build modes; a correct full data-source inventory and ownership of each derived field are recorded. If cache assembly cannot be made faster than the baseline, stop and revisit the design rather than shipping only an endpoint wrapper.

## Step 2: Reconcile current authority and durable source revisions

**Files:** `.lore/reference/specs/collection/collection-filter-sort.md`, `.lore/reference/specs/features/shelf-capacity.md`, `.lore/reference/specs/fitness/niche-champion-display.md`, relevant shared types/schemas in `packages/shared/src/`, `packages/daemon/src/services/storage-service.ts`, source migration helpers, writers in tournament/prediction/niche/redundancy/shelf services and routes, their focused tests.

Reconcile every now-obsolete server-fetch and “No daemon API changes” statement in `.lore/reference/specs/collection/collection-filter-sort.md`, including its overview, Key Decision: Client-Side Only implementation consequence, REQ-CFS-27/29, and success criterion 10; preserve browser-side sorting/filtering requirements. Amend shelf-capacity REQ-SHELF-25 and niche-display REQ-NICHE-33 to allow validated Collection snapshot reuse when all relevant inputs are unchanged, while retaining fresh standalone endpoint computation and current-input semantics. Add revision fields and backward-compatible migration/default initialization for each independent source, including no-op behavior. Persist source data and revision in the same atomic file replacement. Audit every writer, including BGG refresh, normalization, settings, shelf rollback, and direct storage calls. Define the data-dir/collection identity, restart behavior, algorithm version, and BGG staleness expiry used by validators. Centralize committed source-vector publication and coordinate multi-source reads/writes so a snapshot never mixes generations or publishes after a newer commit. If a multi-file operation partially fails, the next read must rebuild from the actual committed files, not an optimistic counter.

**Gate:** focused shared/storage tests demonstrate legacy migration, successful/no-op/failed commits, crash-safe file/revision agreement, fresh vector on restart, races between reads and every independent writer, and expiry without a mutation. A spec audit confirms no stale “server fetches all Collection data” or “no daemon API changes” statements remain, and the shelf/niche spec changes permit only correctly invalidated Collection snapshot reuse while preserving standalone behavior. Browser-side filtering/sorting requirements remain intact. Preserve existing collection revision semantics. Do not claim a cheap validator if obtaining it still reparses every source on each read.

## Step 3: Assemble one compact, variant-correct daemon snapshot

**Files:** new Collection snapshot service/schema and route in `packages/daemon/src/` and `packages/shared/src/`; adapt `displayed-fitness-service.ts`, `capacity-service.ts`, game projection, niche and purchase-utilization projection without changing existing `/api/games` clients; focused daemon/shared tests.

Capture coherent inputs once, share reusable score-independent projection and computation, retain two score/display-score/utilization variants per applicable row, and project niche positions keyed by ID. Include axes, tournament stats, ignored tags, redundancy mode, capacity and page counts needed by existing table without leaking owner notes. Refactor `capacityService.computeCapacity()` so its packing/projection core accepts captured shelf configuration, **raw ordinary scores equivalent to `gameService.listGames()` before prediction/redundancy/utilization**, collection axes, and tournament data; retain the existing storage-loading wrapper for other callers. The snapshot calls the input-taking core under its coherent source vector rather than the wrapper that re-lists/scored games and reloads sources (`capacity-service.ts:64-72,163-174`). Passing adjusted displayed scores would change packing priority and reported capacity fitness. Niches likewise use the owned predicted pre-redundancy universe; only score-independent fields can be shared between display variants. Keep the result schema runtime-validated and deterministic; guard non-finite/invalid computed numbers. If tournament source loading fails, base score assembly cannot proceed (`game-service.ts:712-720`): fail the required snapshot with a retryable unavailable response, never substitute non-tournament scores. If only the optional tournament stats-display projection fails after valid scoring inputs are captured, hide that display; other optional source failures disable only their dependent feature. Such degraded responses are non-cacheable. Maintain existing `/api/games` compatibility until new consumers are proven.

**Gate:** contract/parity tests compare old versus new datasets at varied collection sizes for score source, purchase-utilization display and sorting, niche ranks, ownership filters, `dimensions=missing`, all counts, capacity, and absence of owner-note fields. Capacity parity includes source-vector coherence under a concurrent shelf/tournament edit, and instrumentation asserts one ordinary score assembly per invalidated snapshot rather than an extra `gameService.listGames()` call inside capacity. Tests distinguish required tournament source failure (retryable whole-snapshot error; no score fallback) from optional stats-display failure (non-cacheable partial response), and cover recovery of both. Profile fresh-snapshot compute time and bytes separately; one big response without shared work or a smaller body does not pass this gate.

## Step 4: Daemon memory cache and conditional transport

**Files:** Collection snapshot service/route, `packages/web/lib/daemon.ts`, `lib/daemon-proxy.ts`, `app/api/daemon/[...path]/route.ts`, daemon and web proxy tests.

Cache the last complete snapshot and share one in-flight build among concurrent reads. Return a validator/ETag derived from committed dependency revisions, server/collection identity, representation version, and time expiry. For `If-None-Match`, check the current vector before expensive assembly; return 304 with no body only if the validated complete snapshot is current. Advance cache publication only after committed writes; discard old in-flight results. Forward conditional request headers and 304/ETag through the web proxy, with private revalidation cache headers and no accidental shared cache. Instrument attempts, outcomes, hit/miss reasons, and bytes at these boundaries.

**Gate:** route/proxy tests cover 200→304, invalidation after each source change, old-etag restart/build change, time expiry, concurrent read/write races, no-op mutations, unavailable/degraded sources, and exact empty 304 bodies. Repeated unchanged requests avoid scoring and large transfer; changed requests return fresh, variant-correct data.

## Step 5: Browser persistence, client loading, and interaction preservation

**Files:** `packages/web/app/collection/page.tsx`, `loading.tsx`, `components/collection-table.tsx`, a small snapshot fetch/IndexedDB module and tests, mutation refresh callers, `packages/web/e2e/collection-*.pw.ts`. The client loading/error affordances and responsive feel belong to a designer lane during implementation; do not redesign the table merely to move its data source.

Replace page-level game-array fetching with a lightweight shell and client data boundary. On navigation/reload, read the identity-scoped stored snapshot/ETag asynchronously, conditionally revalidate before displaying it as current, accept 304 only with a matching valid local body, then render the existing table. On a complete validated 200 with a reusable ETag, atomically replace the sole stored entry; on storage errors fall back to network. A degraded 200 without ETag/no-store may render its available portions with explicit unavailable/retry feedback, but must **never** replace the persisted complete snapshot or be treated as a validated cache hit. Its next reload sends the older complete ETag for authoritative revalidation; if the source is still unavailable, the daemon returns degraded 200 again, not 304; after recovery, it may return 304 for the unchanged complete snapshot or 200 with a new complete result. On network failure, show an accessible retry/error state instead of silently serving stale data. Put the topbar controls and table under one Collection snapshot provider (or pass one typed refresh callback): successful `RefreshAllButton` and `NormalizeFitnessButton` operations, plus niche ignore/restore controls within the table, call `onCommittedMutation()`; it invalidates the in-memory validator, discards pre-mutation in-flight results, and requests one fresh snapshot. Do not rely on `router.refresh()` alone to refresh an already-mounted client boundary or re-embed full arrays. Revalidate on focus for changes made on game detail and in other tabs (broadcast may accelerate but never substitutes for authoritative validation). Restore persisted sort/filter/toggle preferences before generating exact-row navigation context or contextual return links. Preserve loading/focus/scroll behavior and no-JavaScript feedback.

**Gate:** component/browser tests cover first visit, warm navigation, full reload 304, changed source 200, missing/invalid/quota-limited IndexedDB, replacement of the sole persisted entry on server/collection identity switch, out-of-order responses, cross-tab focus, transient error/retry, optional failure, mobile loading/error UI, and exact navigation rows after hydration and return. An optional-source degraded 200 displays an unavailable state but leaves the prior IndexedDB entry untouched; on reload it does not get a false 304 while degraded, and recovery revalidates or replaces the complete entry. Exercise real Refresh All, Normalize Fitness, and niche ignore/restore controls against fixtures and assert one fresh snapshot request and changed rows/scores/positions without a large RSC re-embed. Controls, sorting, filters and ownership changes remain client-side where expected and are not lost during revalidation.

## Step 6: End-to-end evidence and handoff

Run focused new tests and existing Collection navigation/controls/thumbnails, purchase utilization, niche/redundancy/tournament/shelf tests, then the branch-wide `bun run typecheck`, `bun run --cwd packages/web typecheck:browser`, `bun run lint`, `bun test`, `bun run build`, relevant Playwright suite, changed-file format checks, and `git diff --check`. Treat **any** failing branch gate as a blocker rather than dismissing it as pre-existing. Compare cold, unchanged reload (304), warm navigation, and post-edit timings/bytes against Step 1 on the same temporary data copy, and verify the original directory fingerprint is unchanged. Record each claim's evidence once; repeat only if relevant code/data changed. Report measured speedup or regression without inventing target numbers. No commit, push, deployment, or Dolt sync without explicit authority.

**Acceptance:** A normal reload and unchanged navigation avoid the three full list computations and multi-megabyte transfer; a relevant edit returns a fresh snapshot with no stale scores/positions/utilization; optional failures recover; all UI contracts hold. A changed request need not be as cheap as 304, but must show a measured improvement against the original post-edit baseline or be called out as not solved.

# Implementation plan for Jev redundancy similarity

> **Status and authority (2026-09-30): Historical approved plan; partially superseded.** The steps below that specify a Jev pair cache embedded in collection state (principally Steps 2, 5, and 6), collection-wide full-manifest delivery/inspection and acknowledgement (Steps 5, 7, and 8), and pre-run frozen transactional coordination/locking assumptions are superseded by the [approved SQLite Jev pair cache redesign](../design/sqlite-jev-pair-cache.md). The redesign places derived pair judgments and run progress in daemon-owned SQLite, uses concise scope/count disclosure rather than mandatory pair-by-pair manifest review, allows edits during a run, and relies on source-identity checks and stale-result discard rather than pair locks. Cleanup of the old collection-embedded cache and manifest workflow is part of the replacement, not optional. This notice preserves the original approved plan for historical discovery; do not implement its superseded steps. Consult the redesign together with the maintained [Redundancy Scoring reference](../../reference/specs/fitness/redundancy-scoring.md), [Owner Game Notes reference](../../reference/specs/current/owner-game-notes.md), and [Jev redundancy similarity design](../design/jev-redundancy-similarity.md) for current contracts. Design approval does not authorize provider calls or imply implementation is complete.

## Goal and authority

Implement the **approved target contract** in the four related references, not the older cosine-only descriptions in historical plans. Existing prediction similarity, shelf placement, cluster niches, personal/tournament ratings, and note CRUD semantics stay intact. Redundancy changes from binary/continuous/personal-axis cosine to binary/continuous factual cosine with optional cached description (C) and authorized owner-note (D) signals. No code work starts merely because this plan exists. No real owner notes are sent during development or tests without a separately initiated, fully disclosed refresh.

At planning time the delivered collection schema is version 8 (`packages/shared/src/validation.ts`); the new semantic state needs a normal sequential schema migration, not reuse of owner-note version-6 migration instructions retained for historical traceability. The current daemon has no TypeSafe capability. The aggregate settings API, semantic collection state, revision fences, and observable similarity status in the amended redundancy reference are *target* APIs, not current code.

## Delivery graph and ownership

1. **Foundations:** factual migration and baseline tests (Step 1), collection-owned semantic state and mutation fences (Step 2), and typed-Jev gateway (Step 3). Steps 2 and 3 can proceed in parallel after shared contracts are defined; they must not share write ownership over wiring files.
2. **Integration:** pure pair scoring (Step 4) depends on 1–2; consent/refresh/cache publication (Step 5) depends on 2–4; artifact lifecycle (Step 6) depends on 2 and 5. Do not activate semantic scoring until publication and invalidation gates pass.
3. **Surfaces:** daemon operations and disclosure (Step 7) depend on 5–6. Web interaction and CLI controls (Step 8) may proceed in parallel with separate file ownership after daemon schemas stabilize. Final full-system validation (Step 9) follows all writers and review.

Implementation ownership: bounded backend/shared/tests by daemon-focused implementers, TypeSafe boundary by an implementer who first checks current API/SDK docs, UI/interaction by a designer, CLI by a separate implementer, and parent-owned reconciliation/validation. Do not parallel-edit `packages/shared/src/types.ts`, `packages/shared/src/validation.ts`, `packages/daemon/src/index.ts`, or `packages/daemon/src/app.ts` across independent lanes; integrate at explicit handoffs.

## Step 1 — Freeze baseline and migrate factual redundancy only

**Changes.** Capture fixtures for current enabled annotation/integrated behavior, saved custom weights (including binary=continuous=0 with personalAxes>0), null/no-neighbor cases, and candidate preview. In `packages/shared/src/types.ts` and `validation.ts`, the stored-source parser (`packages/daemon/src/services/stored-source-revision.ts`), `storage-service.ts`, `routes/redundancy.ts`, and `redundancy-engine.ts`, remove `personalAxes` **only from redundancy settings/calculation**. Preserve current binary/continuous encoding and their ratio; migrate 0/0 to 4:3 and surface the migration notice through the settings read. Keep the shared feature-vector axis fields and prediction/shelf consumers unchanged. Make cosine and threshold behavior finite for zero/empty vectors. Update settings UI and CLI field schemas mechanically only after daemon contract settles; user-facing controls receive visual review in Step 8.

**Gate.** Focused tests in `redundancy-engine.test.ts`, `redundancy-settings-routes.test.ts`, `redundancy-integration.test.ts`, and storage migration tests prove saved ratios, 0/0 recovery, current stage retention, list/detail score parity, finite numbers and no unintended changes to prediction, shelf and niche behavior. Expect intentional offline neighbor/score changes from axis removal; compare them explicitly rather than disguising them as regression-free. No TypeSafe calls and no new note reads.

## Step 2 — Put semantic authority in the collection, not the factual settings file

**Changes.** Add strict semantic state (enablement, F/C/D weights, cached-D-use permission, one-execution authorization identity, numeric pair judgments, published generation and monotonic consent/source epoch) in the next revisioned collection schema and sequential migration (`packages/shared/src/validation.ts`, `types.ts`, `packages/daemon/src/services/collection-migration.ts`, `storage-service.ts`). New and migrated data starts semantic-off, F=7/C=0/D=0, cached-D-use off, no pending authorization or generation. First explicit semantic opt-in proposes F=7/C=5/D=10 unless the owner selects other values. Cache only numeric judgments and minimal model/rubric/source provenance, not descriptions, note text, prompts or explanations. Pin resolved Jev model/rubric identity and symmetric game-pair key; a C result from shared C+D state inherits both note versions, whereas C-only has no note dependency.

Extend the existing serialized `collection-mutation-service.ts` and source vector/freshness contracts. A factual weight PATCH must first durably advance the collection epoch, withdraw a semantic generation and fence refresh, *then* persist `redundancy-settings.json`; failure of the collection write aborts the PATCH, failure of the settings write leaves the old setting file and a withdrawn generation. Other factual-only fields do not need semantic withdrawal. Semantic settings PATCH writes collection state only. `GET /redundancy/settings` composes a read-only aggregate of two authorities without leaking note presence or text. Keep the collection browser projection and snapshot cache source identities updated without exposing semantic cache or consent state in broad responses.

Separate the collection's **write revision** from the refresh's **evidence/eligibility identity**: keep monotonic evidence and consent/semantic-settings epochs plus the separately stored source revisions. An authorized refresh captures these stable identities and its immutable pair-manifest digest. Its own disclosure, authorization, numeric cache checkpoint, publication and normal authorization closure may advance the collection write revision for atomic CAS but must not advance the evidence or consent epochs or invalidate the pair set. Re-read the current collection write revision within each serialized mutation and retry CAS as appropriate; never use that raw revision alone as a cross-request source-staleness predicate. Actual game/note/score-source changes advance evidence identity; revocation or semantic-weight changes advance consent/semantic epoch and fence the active job. Expiring a completed transmission authorization does not affect cached-D-use permission or an already valid published generation.

Before defining the generation identity, map every input to redundancy **eligibility and pre-penalty score**, not just pair similarity: collection games/ownership/BGG/axes/ratings/notes and derived play evidence advance the collection evidence/eligibility epoch, **not** every collection write revision; separately stored tournament results, prediction settings, factual redundancy settings and any other discovered scoring source must contribute their own monotonic revision/epoch through `source-vector.ts`/stored-source tracking. Inspect each writer and prove the evidence revision advances on accepted relevant changes but not on Jev-only bookkeeping. If a writer lacks an authoritative monotonic revision, add one or a durable invalidation fence before enabling semantic publication. A later A→B→A value reversal must not restore an earlier generation. Snapshot the resulting complete eligibility identity and source fingerprint for disclosure, each provider send, publication, persisted profile/display writes and every scored read. A changed identity or recomputed eligible game set aborts unsent requests and withdraws/ignores the generation, including after restart; never trust a one-time eligibility check.

**Gate.** `collection-migration.test.ts`, `storage-collection-migration.test.ts`, `collection-mutation-service.test.ts`, settings routes and snapshot tests cover historical migration, restart, strict validation, zero/nonfinite weights, no two-authority PATCH, collection-before-file failure behavior, A→B→A factual weights across restart, and 200→304→post-edit-200 not serving old fitness. Prove source revisions/epochs are monotonic for **every** score/eligibility source (especially tournament and prediction settings) and no superseded note text enters any durable cache. Change an independently stored score input during refresh and after publication; verify unsent work stops, stale publication fails, readers fall back, and restart does not resurrect the generation. Separately run a multi-pair refresh with intermediate collection-persisted judgments but *no* evidence change: it must finish, publish, close the transmission authorization, remain ready after restart, and never mistake its own write revisions for stale evidence. Do not add persistence without tests for interrupted atomic writes and recovery.

## Step 3 — Add a typed Jev capability behind the daemon gateway

**Changes.** Check live TypeSafe API/SDK, Score/Noul, model pinning, limits, usage and retry docs against installed version before choosing HTTP or SDK. Add a test-injectable typed capability next to (not inside) existing pi-agent grounded analysis (`packages/daemon/src/services/grounded-analysis/provider.ts`, `session-factory.ts`, and production wiring in `index.ts` as needed). Only this gateway owns credentials/config, pinned Jev model, validated state/questions/answers, token budget, rate/concurrency/backoff, cancellation, and redacted attempt/outcome logs. Ask C and D independently over shared state in a single request when both are authorized; C-only contains no owner-note fields, D-only contains no BGG descriptions. D is one Score question, with no separate relevance/firsthand gate; validate and retain confidence as metadata without filtering or downweighting a valid score. Its rubric must not invent experiences absent from the notes. Never log or persist submitted text. A malformed/partial answer fails the requested pair rather than becoming zero or `unavailable`.

**Gate.** Inject a fake provider for ordinary tests; test exact outbound state field sets and prompt-injection-resistant treatment of notes as evidence, strict typed answer validation, token/rate budget, retries/429/529, cancellation and redacted boundary logs. Unit test versioned rubric mapping into [0,1], confidence kept as metadata with no score gating/discount, and sparse/prospective notes without invented play experiences or a second eligibility gate. No live provider test uses owner data; optional smoke test with fictional text requires explicit operator choice.

## Step 4 — Compose complete validated pair scores without I/O in the engine

**Changes.** In `packages/daemon/src/services/redundancy-engine.ts` and callers (`displayed-fitness-service.ts`, `collection-snapshot-service.ts`, `profile-service.ts`), resolve a complete unordered-pair table for the same eligible owned, non-vetoed, positive-score universe. The caller computes the existing factual cosine and, when a valid generation exists, blends F=7/C=5/D=10 or configured weights over available enabled components, omitting truly unavailable inputs. Zero-weight signals need no inference. If publication is absent/stale/incomplete, pass factual-only pairs and safe mode/status. Pure engine accepts caller-validated pairs plus provenance, calculates neighbors/penalties and never reads storage, cache, notes, or a provider. Expose `redundancySimilarityInfo` independently of nullable `redundancyAdjustment` so no-neighbor games still show factual/semantic and ready/not-ready/stale/disabled status.

**Gate.** Unit tests cover C-only, D-only, both, zero weights, absent notes, sparse notes, all missing descriptions, factual fallback, threshold crossings, confidence metadata without gating/downweighting, symmetric pair scores, no-neighbor status, predicted-neighbor authority, annotation/integrated parity, and unchanged niche/prediction paths. A caller test rejects missing/extra pair keys, nonfinite scores and wrong generation/consent/settings identity before the pure engine runs. List/detail, preview, CLI and snapshot agree on the same published generation.

## Step 5 — Implement explicit refresh, consent and atomic generation publication

**Changes.** Add daemon-owned refresh service and strict operations/routes for status, one-execution authorization/disclosure, refresh/cancel, and semantic settings. At request time freeze exactly the owned, scored, positive, non-vetoed games and enumerate the complete sorted unordered pair manifest with a note-bearing flag per pair (not note contents), source/eligibility revision vector, provider/pinned model, retention caveat, budget and possible integrated-score effect. Store a short-lived immutable disclosure identity (manifest digest plus revision vector, pair count, note-pair count and expiry) in the revisioned collection. Expose a paginated manifest read or complete downloadable manifest bound to that identity, with bounded page size and stable ordering; the owner can inspect the **entire exact set**, not only counts. Acknowledgement names the same digest and pair count and is accepted only after full manifest delivery/inspection is available, while the disclosed source vector and eligible set still match. Reject missing/mismatched/expired identities; consent cannot silently expand the pair set. Bind the authorized refresh and each request to that same immutable manifest, with new disclosure after any relevant source change. Authorization for note transmission is **not** cached-D-use permission. Check current eligibility, consent epoch, complete source vector and note versions immediately before each send. D candidates are all pairs with two present notes *before* relevance inference; never preinspect note semantics to narrow disclosure. C-only and D-only send only their respective source texts. Bound 19,900 possible pairs for 200 games with explicit quota, concurrency, progress/cancel and fail-closed budget exhaustion; do not infer all pairs from a normal read. Persist working numeric judgments as allowed but publish only complete coverage of enabled positive-weight signals. A no-longer-current request cannot publish; one-execution authorization is consumed/closed even after restart. Return an explicit incomplete/failure status, not a silently blended partial result.

**Gate.** Mock-provider integration tests prove no calls from note CRUD, ordinary reads, BGG refresh, prediction, wishlist, idle/background work or cache misses. Test multi-page disclosure of the full pair manifest, stable ordering and digest, full download/pagination completion, page-mix and mismatched/expired acknowledgement rejection, source change between first and last page, and no note text in manifest. Test per-pair scope, C-only privacy, D-only privacy, combined C+D cache dependency, expiry, revocation during in-flight inference, budget exhaustion, malformed response, cancellation, provider outage and restart. Publish exactly once after complete coverage; stale completion after note clear or tournament/prediction change may neither persist nor be served. In a no-evidence-change run, checkpoint multiple pairs to the collection, publish, consume authorization, restart, and verify the generation remains ready. Log trigger, attempts/outcomes, pair IDs/versions and usage without text.

## Step 6 — Fence notes, derived artifacts and candidate previews

**Changes.** Use `owner-game-note-service.ts`, `game-service.ts` deletion hooks and `collection-mutation-service.ts` to remove D/shared C results and withdraw generation in the same accepted collection write as set/edit/clear/deletion; even identical-text set advances note version. Pre-invalidate independently persisted D-derived profile/display artifacts with a **targeted** hook in `collection-artifacts.ts`; profile/display writers do final revision/consent check and atomic write within the same serialized coordinator, never while holding it for inference. Readers independently check artifact freshness after restart. Do not clear factual-only wishlist snapshots due to note changes. Preserve existing deletion blockers and previously-owned note retention. In `redundancy-preview.ts`, `bgg-fitness-preview-service.ts`, and `wishlist-service.ts`, make ordinary candidate and persisted wishlist previews factual-only; an optional explicitly requested candidate C comparison is transient and separate from stored preview semantics.

**Gate.** Race test: start shared C+D inference, clear either note, complete the response; verify old C/D never returns or persists, including after restart. Race test: begin profile/display computation, then clear note before artifact publication; stale writer aborts, and the cleared note's score never reappears. Inject purge/collection-write failure, settings write failure, source edit, BGG description refresh, consent disable, permanent deletion and previously-owned transitions. Validate wishlist add/refresh and old snapshots remain factual-only and preserve snapshot-at-save rules. Check persisted artifacts, logs and broad payloads for no old note text or note-presence leak.

## Step 7 — Wire daemon API with stable disclosure and status

**Changes.** Register strict daemon operations in `packages/daemon/src/app.ts` and production deps in `index.ts`; expose factual settings PATCH separately from collection-owned semantic settings/refresh, with explicit one-execution disclosure/authorization acknowledgement and cancellation/status. Keep errors and output bounded, note-free, and discoverable to CLI. Ensure response and snapshot validation includes safe `redundancySimilarityInfo` even when no adjustment exists. Use DI services so provider cannot be reached from generic GET routes. Disclosure summary returns digest, counts, source identity, provider/model, budget and expiry; an explicit bounded manifest endpoint/page or download returns **all exact pairs and their note-bearing flags** under that same frozen digest. Acknowledgement binds digest, complete delivered manifest and current source identity; counts alone are not authorization. Prefer a selected subset if full-collection disclosure/budget is impractical, but never publish partial collection fitness.

**Gate.** Daemon route/operation tests cover strict input, unexpected fields, state transitions, refusal, lost response/retry semantics, stale collection revision, no provider on GET/PATCH/note mutations, `disabled`/`not ready`/`stale`/`ready` statuses, and parity between settings GET and both write stores. Verify CLI discovery can find new operations without private evidence.

## Step 8 — Ship user-facing controls without weakening the boundary

**Changes.** Have a designer implement the web redundancy panel and refresh/consent flow in `packages/web/app/redundancy/page.tsx` and related API/client components: factual vs semantic weights, note-use permission, provider/pair/budget disclosure with inspectable full manifest, progress/cancel, clear status, migration notice, and annotation vs integrated effect. Update **game detail** redundancy section, **collection row/list** indicators, and **search candidate** and **wishlist** preview labels so factual-only, ready, not-ready and stale states are visible even when `redundancyAdjustment` is null/no neighbor; stored wishlist previews explicitly say factual-only when semantic mode is enabled. Do not show note excerpts, imply publisher descriptions are personal experience, or silently enable semantic mode. A separate implementer extends `packages/cli/src/commands/redundancy.ts`, `game`/`scores`/`predict bgg` output and command dispatch for settings, exact-manifest disclosure/refresh, progress/status, cancel, revocation, mode/status/generation and factual-only candidate labels, preserving the same daemon contract. UI may initially support collection-wide refresh; selected-pair exploratory refresh, if implemented, cannot publish collection fitness.

**Gate.** Web component and browser tests check consent denial/C-only path, complete pair-set inspectability, candidate D unavailable, game detail and collection rows with ready/stale/no-neighbor status, search and stored wishlist factual-only labels, screen-reader naming and keyboard behavior, narrow layouts and interrupted refresh. CLI tests check discovery, complete manifest retrieval/acknowledgement, `game`/`scores`/`predict bgg` JSON/human provenance and factual-only labels, explicit authorization, refusal, stale/failure exit status and no note text in output. Review UI copy against the actual provider/retention and score-effect contract.

## Step 9 — Quality, cost and release gate

**Contract amendment (2026-09-30; history preserved).** The original Step 9 calibration work remains **unresolved** until the owner explicitly authorizes calibration under the amended rubric. The prior fictional observation was collected under the former separate relevance-gate rubric and cannot establish the quality, confidence handling, threshold behavior, or calibration of the new single-D-Score contract. Do not reinterpret its result as evidence for the amended rubric. Before semantic release, bump the rubric/question version and invalidate prior-version cached judgments; calibration must use the approved one-Score D question, with confidence as metadata only. Any provider execution still requires separate explicit authorization; no live calls are implied by this amendment.

**Claims and evidence owners.** Backend implementer owns focused state/migration and race evidence (Steps 1–7); typed-boundary implementer owns outbound evidence minimization, model/rubric and failure tests (Step 3/5); designer owns UI interaction/browser evidence; CLI implementer owns discovery parity; parent reconciles source freshness, privacy, and score consistency across all lanes. Use recorded test outputs rather than repeating unchanged focused checks. Run repository-wide `bun run typecheck`, `bun run typecheck:browser`, `bun run lint`, `bun test`, `bun run build`, `bun run test:browser` and formatting checks on final state; treat **any** failing gate on this branch as a merge blocker, including failures unrelated to the edited files. Run a final independent TypeScript/Bun review of daemon, socket, CLI and React boundaries after integration.

Before enabling semantic mode on real data, use a **fictional or owner-approved** set of representative pairs and owner-reviewed expected judgments to calibrate Score levels, threshold effects and F/C/D weights under the amended single-D-Score rubric; confidence remains metadata, not a filter or discount. Record observed request tokens, latency and budget for collection-sized coverage. Mocked tests establish correctness of control flow, not judgment quality. If Jev quality, cost, provider retention or authorization UX is unacceptable, retain factual-only mode and report that limitation instead of silently claiming the semantic feature is ready. No automatic live-data smoke call is part of the test suite.

# Implementation plan: wishlist Jev description similarity

> **Approval and authorization:** The owner approved this plan on 2026-10-03 and authorized implementation to begin after this bootstrap is committed. The owner-approved design is [Wishlist-to-owned description similarity](../design/wishlist-jev-description-similarity.md). Commit a checkpoint after every implementation bead; do not push. The parent owns final implementation validation/review.

## Goal and fixed contract

Implement the approved wishlist-candidate-to-eligible-owned description signal, preserving saved prediction snapshots and adding a separate current redundancy projection. The candidate has no owner-note signal. In cache terminology **C is description** and **D is owner-note**: candidate requests and candidate reuse are C_ONLY; never consume D or C from a shared C+D request. Reuse the current per-pair F/C/O blend (O denotes owner-note in the formula, but is absent for wishlist candidates), omitting unavailable signal and its weight from the denominator while retaining valid zeroes. Candidate fitness/strongest-owned-overlap use existing redundancy behavior; there is no separate ranker.

The existing implementation does not yet provide these capabilities. The current wishlist contract says semantic comparison is transient-only, `WishlistEntry` has no compact BGG scoring source, and collection Jev resolution assumes collection pair scope. Implementation must first amend those authorities rather than treating this plan or the design as delivered behavior. In particular, reconcile `.lore/reference/specs/features/wishlist.md`, `.lore/reference/specs/current/owner-game-notes.md`, and `.lore/reference/specs/fitness/redundancy-scoring.md` with the approved design; the current per-pair correction in owner-game-notes supersedes its conflicting historical complete-coverage clauses.

## Architecture facts that constrain the work

- `packages/shared/src/types.ts` defines `WishlistEntry`; `packages/daemon/src/services/storage-service.ts` loads/saves wishlist JSON as raw JSON, while `packages/daemon/src/services/collection-artifacts.ts` has separate salvage/validation paths that must preserve new fields.
- `packages/daemon/src/services/wishlist-service.ts` owns add/refresh/refreshAll and builds saved snapshots. `prediction-service.ts` currently requests a rich scoring Thing (`getBoardgameScoringInput`) for BGG preview; that source is not persisted on the wishlist. `bgg-xml-parser.ts` parses verified Thing source, and prediction construction currently creates a transient candidate representation.
- The factual encoder in `feature-vector.ts` reads mechanic/category names plus BGG weight/community rating and min/max/best players/playing time. Vocabulary and continuous ranges are rebuilt from current collection games with BGG data (`redundancy-factual.ts`, `redundancy-preview.ts`); do not persist derived vectors/ranges.
- `jev-pair-cache-service.ts` keys judgments by collection ID, pair IDs and signal; dependencies record name/description/note fingerprints and contract provenance. `jev-pair-identity.ts` hashes exact unnormalized source text. `jev-pair-read-proof.ts` permits validated C_ONLY reads without cached-note-use permission; note-dependent shared C+D is not a candidate cache hit.
- `computeRedundancyAnalysis` validates a complete collection-owned pair table (`redundancy-engine.ts`). Candidate-vs-owned pairs are an incomplete, distinct universe; reuse shared blend/neighbor/penalty arithmetic at a candidate-only boundary and do not pass that partial table to the collection engine.
- Jev runs are explicit-start only. `jev-run-controller.ts`, `jev-run-source-adapter.ts`, `jev-run-scope.ts`, and `jev-run-service.ts` provide immutable captured scope, source/policy fencing, explicit aggregate disclosure, lazy gateway construction, progress, cancellation, pair checkpoints and final validation. Extend this machinery rather than adding inference to wishlist reads.
- Acquisition currently crosses independent authorities: `packages/daemon/src/services/game-service.ts:addGame` commits the collection mutation, then `packages/daemon/src/routes/games.ts` calls `wishlistService.removeByBggId` and suppresses cleanup errors. `createApp` composes these services; daemon startup constructs the collection mutation service/cache before app routes, with no wishlist-acquisition reconciler today. Replace the route's best-effort sequence with one coordinated acquisition entry point and explicit recovery; do not claim a cross-file transaction.
- Wishlist web sorting currently uses saved `redundancyPreview.adjustedScore`; the page, API/proxy and CLI must consume the proposed separate current projection. Keep predicted-score sorting unchanged.

## Execution sequence

Each phase is a stop gate: preserve its behavior and tests before proceeding. Update the three current references and the relevant current Jev/cache contract before shipping behavior. Existing paths below are targets, not claims that exact new functions or routes already exist.

## Non-negotiable performance constraints and evidence

Jev has already required multiple performance passes. Preserve its established capture/index/memoization, point-lookup, proof-reuse and serialized-dispatch patterns; correctness-preserving code that rebuilds or rescans the same universe is still a blocker. The implementation may not trade these constraints for a shorter delivery or a new unmeasured concurrency scheme. Tests must record structural operation counts (factory/lookup/encode/gateway/checkpoint calls) rather than inventing wall-clock thresholds.

- **One coherent capture, one shared factual context:** build one `createRedundancyFactualContext` and one memoized eligible-owned lookup/index for each coherent current collection/candidate result capture. Its vocabulary and continuous ranges are computed once; memoize each distinct collection/candidate feature vector once per context. All wishlist candidates in the same capture share these structures. Do not rebuild context or owned vector set per candidate or pair. This follows `jev-pair-coverage.ts:229-230`, `redundancy-factual.ts:10-37`, and `feature-vector.ts` memoization.
- **Only requested candidate-to-eligible-owned work:** candidate cache operations and pair calculations are limited to the requested candidate×eligible-owned pairs. Do not create owned-owned comparisons, enumerate the entire SQLite judgments table to find hits, or rebuild a full collection map per source fence. Use indexed point lookup/key access and one memoized owned lookup per unchanged capture, as `jev-run-service.ts:375-383` does with `createJevRunCollectionLookup`; preserve `jev-run-scope.ts:235-259`'s direct scan fallback rather than constructing a new full Map for each fresh fence. Existing SQLite statements are keyed `SELECT`/upsert point operations (`jev-pair-cache-service.ts:310-331, 535-581`); no batch API currently exists. Do not claim one or introduce it without a separately reviewed, bounded and validated change.
- **Reuse coherent proofs, not repeated lookups:** resolve a read proof once per coherent result and validate its cache mutation revision around projection. Extend proof identity to candidate source/membership, owned eligibility/source, factual/semantic weights and policy. When those sources and `mutationRevision` are unchanged, repeated currentness checks and cheap status polls must not re-query every pair. Candidate/owned source changes, eligibility/policy changes, and cache mutation (including purge/rekey) advance or invalidate the proof; cache read/revision errors fail closed, never authorize a trusted miss or stale result. Preserve the no-rescan proof pattern in `jev-pair-read-service.ts:142-190`.
- **Keep inference bounded and sequential:** `jev-run-service.ts:412-463` processes the planned pairs serially, constructs its gateway lazily, and skips cache hits before evaluating a request. Preserve this scheduler, request budgets, rate limits, backpressure and cancellation. Do not add `Promise.all`, an unbounded worker pool, or new concurrency dependencies. A concurrency change requires separate measured design/approval and is not in this scope. A complete hit-only run creates zero gateways and makes zero provider requests. Each successful provider pair uses the existing atomic `checkpointPair` transaction to save its judgment(s) and associated progress together (`jev-pair-cache-service.ts:661-687`); do not split C_ONLY judgment and progress into separate upsert/progress writes. Do not assert that run lifecycle performs no progress-only writes.
- **Separate cheap status from expensive projection:** preserve the current cheap progress poll (60-second polling/manual refresh in `packages/web/app/redundancy/page.tsx:74-76, 309-339`) separately from full semantic status/coverage reads and candidate redundancy projection. Make counts candidate-aware; status ticks must not trigger a whole wishlist scoring rebuild or all pair lookups. Ordinary wishlist list/sort has zero BGG and Jev gateway work; a current projection computes once per coherent request capture.

Evidence owners: Phase 2-3 daemon scoring tests own context/vector counts; Phase 4 cache/read-proof tests own lookup/revision/rekey counts; Phase 5 the fake-gateway/temp-SQLite composition harness owns request/checkpoint counts; Phase 6 web/API tests own poll/projection invocation counts. ### 3. Add candidate-only blend and current result projection

**Owner lane:** daemon backend, with shared contract owner.

**Targets:** `packages/daemon/src/services/feature-vector.ts`, `redundancy-factual.ts`, `redundancy-preview.ts`, `redundancy-engine.ts`, wishlist read/service/route composition and shared response types.

**Work:** construct the candidate factual projection from persisted compact source and rebuild its vector against the same current collection source universe and normalization used by factual preview. Resolve eligible owned neighbors under current scoring eligibility. Reuse current F/C weighted blend and existing neighbor/penalty arithmetic only for candidate-to-owned pairs; do not send an incomplete candidate pair table to `computeRedundancyAnalysis`, request owned-owned inference, or change owned penalties. Keep saved base `predictedScore` as adjustment original score and apply the resulting adjustment exactly once. Zero neighbors means a valid zero penalty and base adjusted score. If no compact source exists, no current blend is computable: use saved factual preview, then base score; never fabricate F from description or cache. Missing/stale C with factual input falls back to F per pair. A valid saved prediction stays rankable regardless of cache availability.

Expose the computed current comparison/adjustment separately from the durable entry, with enough provenance to distinguish current blended, saved factual fallback, and base-score fallback. Do not mutate `predictedScore` or `redundancyPreview` during reads or Jev cache changes. Keep prediction-score sort unchanged; redundancy sorting consumes the stated precedence.

**Tests:** daemon service/route tests for differing saved/current adjustments, missing or stale C with F fallback, legacy source absence, zero neighbors, no saved adjustment, and base score unchanged. Add small hand-computed numeric fixtures for F-only, F+C, valid C=0 (C weight remains in denominator), disabled/zero-weight C, and mixed pair availability; assert exact normalized values, threshold neighbor membership, and resulting penalty/adjusted score. Verify factual normalization uses current `collection.games` with BGG data including ineligible-as-neighbor games, while candidate neighbors are exactly owned, scored, positive-score, non-vetoed games (excluding previously-owned, vetoed, null/nonpositive score, and wishlist candidates). Include an ineligible game whose source changes vocabulary/ranges and changes F but never becomes a neighbor. Reload persisted compact source and assert same F offline. Instrument the scorer to assert one factual-context/vocabulary/range build per coherent capture and at most one vector encoding per distinct game; include deterministic multi-candidate operation counts proportional to requested candidate×eligible-owned pairs and zero owned-owned comparisons. Engine boundary tests prove candidate-only rows never enter full collection table validation and never change owned adjustments. Assert serialized wishlist JSON remains byte/value-equivalent across comparison reads and Jev cache changes.

**Stop gate:** candidate projection works without collection-engine pair-universe violations and each candidate receives at most one penalty application.

### 4. Extend cache identity/read proof and acquisition lifecycle

**Owner lane:** daemon/cache backend; source-mutation coordinator owner.

**Targets:** `jev-pair-cache-service.ts`, `jev-pair-identity.ts`, `jev-pair-read-service.ts`, `jev-pair-read-proof.ts`, `jev-pair-coverage.ts`, `jev-mutation-impact.ts`, `game-service.ts`, `routes/games.ts`, `app.ts`, and daemon startup/reconciliation in `packages/daemon/src/index.ts`.

**Work:** add an explicit pair-domain discriminator to the SQLite identity/key contract (existing rows migrate/read as collection domain; wishlist candidate pairs use candidate domain). A row domain alone does not disambiguate its two members: cache key canonicalization and dependency identity currently treat member IDs as untyped strings, and local IDs may be arbitrary strings. In the candidate domain encode each member as a reversible, unambiguous canonical tuple, for example `JSON.stringify(["wishlist-bgg", collectionId, bggId])` for the candidate and `JSON.stringify(["owned-local", collectionId, localGameId])` for the owned game. Include the collection ID in both typed tuples, retain the row-level pair-domain discriminator, and use the typed member IDs consistently in pair ordering/key creation, dependency fingerprints, lookup/read proof, validation, and candidate purge. Do not use assumed-unique string prefixes or raw BGG/local IDs in candidate-domain keys. Collection readers enumerate only collection-domain rows. On acquisition, a single SQLite transaction converts both typed candidate-domain members to the existing raw local-game member IDs and changes the row to collection domain only after full source/provenance/eligibility proof; no typed candidate key or dependency ID may leak into the owned reader. Candidate reads validate persisted wishlist source identity/name and both description fingerprints, owned identity/name/description and eligibility, effective settings/source policy, model/rubric/question/request-schema/score-mapping provenance, and C_ONLY dependency kind. Never accept D_ONLY or SHARED_CD for candidate C. Do not copy raw description into SQLite or logs. Cache absence/corruption is a miss, not a lost prediction.

Replace best-effort acquisition cleanup in `routes/games.ts` with one coordinated acquisition entry point spanning `gameService.addGame`, wishlist state and Jev cache. Use `profileSourceCoordinatorFor(storageService)` for short serialized mutation/finalization sections, not across BGG or Jev network calls. Keep existing collection mutation authoritative and do not claim rollback across collection JSON, wishlist JSON and SQLite. Order: (a) commit the game through the collection mutation service; (b) once owned, immediately exclude that BGG ID from candidate preparation, reads and late response publication, even if later cleanup fails; (c) idempotently rekey each provably compatible C_ONLY row in one SQLite transaction, preserving value, original `completedAt` and provenance; (d) remove the wishlist entry only after transfer/rejection-and-purge handling succeeds. If step (a) fails, leave wishlist and candidate rows untouched. If collection commit succeeds but transfer/cache work fails, retain the wishlist source/entry as recovery evidence, return a truthful partial failure (never generic success), and ensure it is hidden/unsendable because the BGG ID is owned. At daemon startup in `index.ts`, before `createApp` exposes routes, reconcile wishlist/owned BGG-ID overlaps from durable collection and wishlist snapshots: retry compatible transfer, safely purge incompatible candidate rows, then remove the entry. Candidate list/read/run paths must also exclude overlaps and fail closed if required reconciliation cannot complete; this closes the gap if startup cleanup itself fails. If transfer succeeds but wishlist save fails, replay is idempotent and preserves original provenance. This derives pending work from the durable overlap; add no separate journal because the source identities and candidate cache dependencies are sufficient to retry. Ordinary user removal/clear is distinct: under the same coordinator, fence in-flight work, purge candidate rows, then persist removal. Late responses must recheck membership and ownership before publication.

**Tests:** `jev-pair-read-proof`, `jev-pair-coverage`, `jev-pair-cache-lifecycle`, `jev-mutation-impact`, wishlist service/routes tests, and game-add route tests. Cover collection-domain migration for existing cache rows and candidate/collection domain isolation. Prove exact-equal candidate BGG/local IDs are not self-pairs, reversed member roles (`candidate 123 / owned 456` versus `candidate 456 / owned 123`) create distinct readable keys, and purging candidate 123 leaves the candidate-456 comparison intact. Verify typed dependencies participate in lookup/proof/fingerprint/purge consistently, while C_ONLY is accepted by the owned reader without cached-D permission and shared C+D is rejected. Instrument point lookups/proof resolution to ensure no full cache enumeration and no repeat pair queries on an unchanged cache mutation revision; source or cache revision change must invalidate proof. Cover every provenance/source mismatch and exact acquisition conversion to raw owned IDs, preserving value, original completion/provenance and owned-reader acceptance with no gateway call. Exercise ordinary removal purge and stale late response rejection. Exercise failure matrix: collection commit fails (nothing changes); commit succeeds but SQLite transfer fails (entry retained but hidden/unsendable and partial failure returned); SQLite transfer succeeds but wishlist save fails (entry remains recovery evidence; retry is idempotent); restart with overlap completes transfer/cleanup before candidate routes are exposed. Also test acquisition races with active run, cache unavailable/reconciler unavailable fail-closed behavior, and transfer rejection due to source or eligibility mismatch.

**Stop gate:** no candidate row can enter collection coverage; compatible acquisition is accepted by existing owned reader; unsafe or partially matching rows are never transferred; a committed acquisition can never be reported as fully successful while transfer/removal recovery is pending, nor can its surviving wishlist row be read or submitted as a candidate.

### 7. End-to-end and final validation

**Owner lane:** implementation integrator; final whole-branch validation and review are owned by the parent.

**Acceptance scenario:** add candidate from a verified BGG Thing and persist compact source; prepare an explicit wishlist Run, hydrate/persist any legacy source before displaying frozen candidate/pair counts and provider disclosure, authorize and start only that scope, then submit only missing C_ONLY pairs; calculate current candidate adjustment with one penalty. Restart and score offline using persisted source and valid cache; refresh source and prove changed fingerprints fence old C while failed refresh preserves old source. Acquire candidate and verify compatible C_ONLY rows transfer without inference and the owned reader accepts them without note permission; inject a cache-transfer failure after collection commit, verify the wishlist record is hidden/unsendable and the route reports partial failure, then restart and reconcile transfer/cleanup. Separately remove/clear a candidate and prove its rows purge and late responses cannot recreate them. Compare saved-vs-current projection fallback while preserving the saved prediction and factual preview throughout. For candidate F, run numeric fixtures for all blend availability cases and a normalization fixture where an ineligible collection game changes current ranges/vocabulary but is never considered a neighbor.

**Privacy/quality limits:** all provider paths in implementation tests use fakes; do not make real provider transmissions or access owner data. ## Decision

The approved design is implementable with existing BGG Thing hydration, feature encoding, explicit Jev run, pair cache, and source-coordination machinery. The cache boundary is decided here: add an explicit candidate-versus-collection pair-domain discriminator, migrate existing rows as collection-domain rows, and use reversible canonical typed tuple identities for both wishlist BGG and owned local members inside candidate pairs; convert to raw local IDs only during verified acquisition transfer. Acquisition is a collection-first recoverable sequence: the durable owned/wishlist BGG-ID overlap fences candidate use; SQLite transfer is idempotent; wishlist cleanup follows; startup reconciliation finishes pending work before routes are exposed, and fails closed if recovery is unavailable. Wishlist run preparation hydrates legacy source before a frozen disclosure, while start only validates and consumes that frozen authorization. The owner approved implementation; each bead requires implementation, separate read-only test verification, separate review, and a parent-owned checkpoint commit. No push is authorized.
